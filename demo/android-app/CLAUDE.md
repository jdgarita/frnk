# demo-android

Internal smoke harness for the toolkit on Android. **Not shipped.** Used to manually verify the public surface (Koin wiring, MVI flow, atoms) without standing up a separate consumer repo.

`com.android.application` — this is the only `application` module in the project. Everything else is a library.

The actual demo UI (`DemoScreen`, `DemoViewModel`, `demoModule`, the fakes) lives in **`:demo-shared`** so it's shared with `iosDemoApp`. This module is just the thin Android host around it.

## Contents

- `DemoApplication.kt` — calls `bootstrapDemoKoin()` (from `:demo-shared`), the single Koin entry point both demo apps share. It first sets `DatabaseContext.application` (`:core-di` — the demo bypasses `initializeFrnk`, so the SQL driver seam is wired by hand), installs `demoModule` (fake `EntitlementManager` + logging fakes), and then — **Android only** — overrides bindings with real toolkit modules (via Koin `allowOverride(true)`) to smoke-test the SDKs on a device: the real `firebaseObservabilityModule` for Firebase Analytics + Crashlytics (BACKLOG P1-5); the real SQLDelight path `databaseModule` (`:data-db-impl`, the platform `SqlDriverFactory`) + `demoNotesModule` (`:demo-shared`, the demo-owned `DemoDB` schema + `SqlDelightNoteStore`, restructure Stage 4 / OQ-2) replacing the in-memory `FakeNoteStore`; and the real `revenueCatModule` for RevenueCat entitlements (BACKLOG P3-2). The RevenueCat override is installed **only when** a public Android SDK key is present in `local.properties` (`REVENUECAT_ANDROID_API_KEY`, surfaced as `BuildConfig.REVENUECAT_ANDROID_API_KEY`); `DemoApplication` calls `Purchases.configure(...)` first, then overrides. With no key the demo falls back to the in-memory fake (Toggle Pro). `revenueCatModule` comes from the direct `projects.monetizationImpl` dep; `libs.revenuecat.core` is also a direct dep (for the host's `configure` call). `iosDemoApp` keeps the same logging-fake bindings for `demoModule` (including `FakeNoteStore` — DemoKit stays free of the SQLite driver), but additionally installs the **CrashKiOS** unhandled-exception hook + `FirebaseApp.configure()` in Swift so the "Force crash" panic button reports to Crashlytics there too (BACKLOG P1-5b) — so `DemoKit` is no longer fully SDK-free on iOS.
- `MainActivity.kt` — the **single launcher** and the device home for `:ui-app`'s **`FrnkAppScaffold`** (the batteries-included app root the toolkit tells real hosts to use; `:demo-shared` can't exercise it — it doesn't depend on `:ui-app`). Calls `enableEdgeToEdge()`, hoists an `AppearanceController` to drive the system-bar icon contrast (`isAppearanceLightStatusBars` / `…NavigationBars`) off the in-app theme, then resolves the shared `DemoViewModel` and feeds the **scaffold-agnostic demo content builders** from `:demo-shared` (`demoFeatureItem`/`demoHostRoutes()`/`demoHomeTopBar()`/`DemoHomeContent`/`demoFeatureEntries`/`rememberDemoSettingsState`/`demoSettingsHandler`/`DemoEffectCollector`/`demoOnboardingPages`/`demoPaywallFeatures`) into `FrnkAppScaffold`. Those same builders drive the iOS `DemoScreen` over `FrnkTabbedNavScaffold`, so both platforms render one demo from one source. It injects the demo's custom Settings (god-mode Developer section) via `FrnkAppScaffold`'s `settingsState`/`settingsEffects` overrides, and relies on the scaffold to auto-mount the paywall + first-launch onboarding (so `demoFeatureEntries` omits the paywall and there's no `FrnkFirstLaunchOnboardingEffect` here). Boots over the Koin graph `DemoApplication` started with `bootstrapDemoKoin()` (which satisfies `FrnkAppScaffold`'s `requireFrnkKoin()`); it does **not** call `initializeFrnk(context)` — that fresh-host overload is documented in `docs/HOST_INTEGRATION.md` §4. MVI effects are surfaced as toasts.
- Custom launcher icon: adaptive-icon XML in `res/mipmap-anydpi-v26/` (`ic_launcher` + `ic_launcher_round`) over `res/values/colors.xml` (`ic_launcher_background`), with `ic_launcher_foreground` PNGs per density. `android:label` and the iOS bundle display name are both just **"frnk"** (visual only — internal package/identifiers stay `…frnk.demo`).

## Build quirks

- This is the only module that applies `com.android.application`. It does **not** apply `kotlin.android` — AGP 9's built-in Kotlin support compiles its sources. Don't re-add the `kotlin.android` plugin. It **does** apply the `kotlin.compose` *compiler* plugin — that attaches to AGP's built-in Kotlin the same way and is fine; only the Kotlin *Gradle* plugin (`kotlin.android`/`kotlin.multiplatform`) must stay off. (The `kotlin.serialization` compiler plugin + the `icons.lucide` dep were dropped once `AppScaffoldSmokeActivity` was deleted — the demo's `@Serializable` routes + Lucide feature-tab icon now live entirely in `:demo-shared`.)
- Applies the `google-services` + `firebase-crashlytics` Gradle plugins so `google-services.json` (project `frnk-demo`) is processed and Firebase auto-inits — the one real-SDK exception to the otherwise SDK-free harness, needed for the P1-5 analytics/crash smoke test. The toolkit's shared modules don't apply these (a consumer app does); they live here only because this is the device-runnable host.
- `release` build type has `isMinifyEnabled = false`. This is a harness; release-mode validation belongs in a real consumer app.
- Depends on the individual toolkit modules it uses, like a real host (the aggregators died at restructure Stage 1): `projects.uiApp` (`FrnkAppScaffold`), `projects.analyticsImpl` (`firebaseObservabilityModule`), `projects.monetizationImpl` (`revenueCatModule`), `projects.dataDbImpl` (`databaseModule` — the real `SqlDriverFactory` behind the demo's `DemoDB`), `projects.remoteConfigImpl` (`remoteConfigModule`), `projects.coreDi` (`DatabaseContext`) — plus `projects.demoShared` (the shared demo UI; atoms/theme/scaffolds/utils arrive transitively through its `api()` deps).

## Rules

- Treat this module as **disposable**. Don't put production logic here; reusable UI goes into the appropriate `shared-*` module, demo UI goes into `:demo-shared`.
- The demo's Koin setup is intentionally minimal (`demoModule` only). If you want to demonstrate `initializeFrnk(...)` end-to-end, swap `DemoApplication.onCreate()` to call it directly rather than expanding the demo wiring.
- Every new toolkit feature is demoed in all three layers — `:demo-shared` (cross-platform), here (`demo-android`, runs on a device), and `iosDemoApp` (builds `DemoKit.xcframework`, runs in a simulator).

# demo-android

Internal smoke harness for the toolkit on Android. **Not shipped.** Used to manually verify the public surface (Koin wiring, MVI flow, atoms) without standing up a separate consumer repo.

`com.android.application` — this is the only `application` module in the project. Everything else is a library.

The actual demo UI (`FrnkDemoApp`, `DemoViewModel`, `frnkAppModule`, the fakes) lives in **`:demo-shared`** so it's shared with `iosDemoApp`. This module is just the thin Android host around it.

## Contents

- `DemoApplication.kt` — calls `bootstrapDemoKoin(sentry, postHog)` (from `:demo-shared`), the single Koin entry point both demo apps share. It first sets `DatabaseContext.application` (`:core-di` — the demo bypasses `initializeFrnk`, so the Room seam is wired by hand), builds the **mandatory** Sentry config from `BuildConfig.SENTRY_DSN` (read from `local.properties`, **required** — the demo is a real host, a blank DSN fails inside the config with a message naming it; there is no logging fake) plus a `PostHogAnalyticsConfig(environment, debug = BuildConfig.DEBUG)` that only turns on SDK diagnostics — the PostHog key is the toolkit's (`FrnkPostHogProject`), never the host's, and then — **Android only** — overrides the demo's fakes (`frnkAppModule`: fake `EntitlementProvider`, identity, `KeyValueStore`, `NoteStore`) with real toolkit modules (a plain module list under Koin `allowOverride(true)`) to smoke-test the SDKs on a device: the real Room path `databaseModule` (`:data-db-impl`, the platform `DatabaseFactory`) + `demoNotesModule` (`:demo-shared`, the demo-owned `DemoDatabase` schema + `RoomNoteStore`, restructure Stage 4 / OQ-2) replacing the in-memory `FakeNoteStore`; and the real `revenueCatModule` for RevenueCat entitlements (BACKLOG P3-2). The RevenueCat override is installed **only when** a public Android SDK key is present in `local.properties` (`REVENUECAT_ANDROID_API_KEY`, surfaced as `BuildConfig.REVENUECAT_ANDROID_API_KEY`); `DemoApplication` calls `Purchases.configure(...)` first, then overrides. With no key the demo falls back to the in-memory fake (Toggle Pro). `revenueCatModule` comes from the direct `projects.monetizationImpl` dep; `libs.revenuecat.core` is also a direct dep (for the host's `configure` call). `iosDemoApp` keeps the same fakes (including `FakeNoteStore` — DemoKit stays free of the bundled SQLite driver) and reads its keys from `Configuration/Secrets.xcconfig` via `Info.plist` in `bootstrapDemoKoinWithSdks()`; the "Force crash" panic button reports to Sentry on both platforms (Sentry's own unhandled-exception hook — no CrashKiOS).
- `MainActivity.kt` — the **single launcher** and a **thin Android platform host**. It owns only the Android-platform concerns — `enableEdgeToEdge()`, hoisting an `AppearanceController` to drive the system-bar icon contrast (`isAppearanceLightStatusBars` / `…NavigationBars`) off the in-app theme, and surfacing MVI effects as toasts (via the `Context.toast(message)` extension in `ext/ContextExt.kt` — the one place toast plumbing lives; reuse it instead of inlining `Toast.makeText`) — then hands off to **`:demo-shared`'s `FrnkDemoApp`**, the unified shared entry point that calls `:ui-app`'s **`FrnkApp`**. `FrnkDemoApp` supplies the demo's own root navigation module (registering `FrnkRootRoute.Onboarding`/`Tab`/`Paywall`, with the `Tab` destination mounting `FrnkNestedNavScaffold(tabs = …)`) and wires its own paywall, onboarding, and custom Settings — so the iOS `MainViewController` calls the exact same composable, both platforms rendering one demo from one source. Boots over the Koin graph `DemoApplication` started with `bootstrapDemoKoin()` (which satisfies `FrnkApp`'s `requireFrnkKoin()`); it does **not** call `initializeFrnk(context)` — that fresh-host overload is documented in `docs/HOST_INTEGRATION.md` §4.
- Custom launcher icon: adaptive-icon XML in `res/mipmap-anydpi-v26/` (`ic_launcher` + `ic_launcher_round`) over `res/values/colors.xml` (`ic_launcher_background`), with `ic_launcher_foreground` PNGs per density. `android:label` and the iOS bundle display name are both just **"frnk"** (visual only — internal package/identifiers stay `…frnk.demo`).

## Build quirks

- This is the only module that applies `com.android.application`. It does **not** apply `kotlin.android` — AGP 9's built-in Kotlin support compiles its sources. Don't re-add the `kotlin.android` plugin. It **does** apply the `kotlin.compose` *compiler* plugin — that attaches to AGP's built-in Kotlin the same way and is fine; only the Kotlin *Gradle* plugin (`kotlin.android`/`kotlin.multiplatform`) must stay off. (The `kotlin.serialization` compiler plugin + the `icons.lucide` dep were dropped once `AppScaffoldSmokeActivity` was deleted — the demo's `@Serializable` routes + Lucide feature-tab icon now live entirely in `:demo-shared`.)
- **No Firebase.** The demo applies no `google-services` plugin and carries no `google-services.json`: remote config stays on the toolkit's no-op default (the "Capabilities" section shows the bundled fallback) and identity is RevenueCat's or the in-memory fake. Crash reporting is Sentry's, via the `frnk.android.sentry` plugin this module applies. Hosts that use Firebase Auth / Remote Config apply the `frnk.android.firebase` convention plugin (`build-logic`) themselves.
- `release` build type has `isMinifyEnabled = false`. This is a harness; release-mode validation belongs in a real consumer app.
- Depends on the individual toolkit modules it uses, like a real host (the aggregators died at restructure Stage 1): `projects.uiApp` (`FrnkApp`), `projects.analyticsPosthog` + `projects.crashSentry` (the `PostHogAnalyticsConfig` / `SentryCrashReportingConfig` types — the mandatory observability pair), `projects.monetizationImpl` (`revenueCatModule`), `projects.dataDbImpl` (`databaseModule` — the real `DatabaseFactory` behind the demo's `DemoDatabase`), `projects.coreDi` (`DatabaseContext`) — plus `projects.demoShared` (the shared demo UI; atoms/theme/scaffolds/utils arrive transitively through its `api()` deps).

## Rules

- Treat this module as **disposable**. Don't put production logic here; reusable UI goes into the appropriate `shared-*` module, demo UI goes into `:demo-shared`.
- The demo's Koin setup is intentionally minimal (`frnkAppModule` + the mandatory observability pair). If you want to demonstrate `initializeFrnk(...)` end-to-end, swap `DemoApplication.onCreate()` to call it directly rather than expanding the demo wiring.
- Every new toolkit feature is demoed in all three layers — `:demo-shared` (cross-platform), here (`demo-android`, runs on a device), and `iosDemoApp` (builds `DemoKit.xcframework`, runs in a simulator).

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`frnk` is a Kotlin Multiplatform + Compose Multiplatform **toolkit** (not a standalone app) intended to be consumed by downstream apps as a Git submodule via a Gradle composite build (`includeBuild("../frnk")`). The `demo/` directory (`demo/android-app`, `demo/ios-app`, `demo/shared`) exists only as internal smoke harnesses — they are not the shipping product.

Read `docs/ARCHITECTURE.md` first when reasoning about cross-module changes; it is the canonical description of the module graph and the api/impl split.

This repo keeps a clean split between **stable rules/reference** (these CLAUDE.md files + `docs/` + `README.md` + `REQUIREMENTS.md`) and **living knowledge** (the MobiAI brain at `.mobiai/brain/`). The brain holds the *why* behind decisions, integration quirks (Firebase/RevenueCat/dSYM), testing patterns, and bugfixes/workarounds — the things that change or carry history.

## Common commands

Bootstrap (one-time per checkout):
```bash
cp local.properties.template local.properties   # then fill in Firebase keys; BuildKonfig reads from this
```

Day-to-day:
```bash
./gradlew compileAndroidMain                # fast compile-only check (the standard pre-push gate — covers commonMain+androidMain for every KMP module); Gradle parallelises across modules
./gradlew testAndroidHostTest               # commonTest + androidHostTest across all KMP modules (the standard pre-push gate); :demo-android uses testDebugUnitTest
./gradlew :data-prefs-api:testAndroidHostTest   # run a single module's tests
./gradlew ktlintFormat                      # auto-fix style (also runs from the pre-commit hook)
./gradlew assemble                          # full build of every target — only when producing release artifacts
./gradlew :demo-shared:assembleDemoKitDebugXCFramework  # produce demo/shared/build/XCFrameworks/debug/DemoKit.xcframework (demo/ios-app consumes this)
./gradlew clean
```

`local.properties` is gitignored and required — `BuildKonfig` will fail at configuration time without `FIREBASE_*` and `BUILD_VARIANT`.

`iosDemoApp` needs local setup beyond `local.properties`: drop in its own `GoogleService-Info.plist` and let Xcode resolve Swift packages on first open (Firebase SDK). Both are gitignored — `GoogleService-Info.plist` and the Xcode-managed `**/xcshareddata/swiftpm/Package.resolved` — so a fresh checkout of the demo isn't buildable from CI (which never builds iOS anyway); it's a local-only harness.

## Toolchain pinning (don't fight it)

- **JDK 17** everywhere. Android Studio bundles JDK 21; the Foojay resolver in `settings.gradle.kts` auto-provisions 17, and the `frnk.kmp.library` convention plugin calls `kotlin { jvmToolchain(17) }` for every standard module because AGP's javac and the Kotlin task would otherwise disagree about target. Don't change this without changing both sides.
- **Kotlin 2.4.10 + AGP 9.4.0 + Gradle 9.6.0.** AGP 9 forbids combining `org.jetbrains.kotlin.multiplatform` with `com.android.library` in the same subproject — every KMP-Android module here applies `com.android.kotlin.multiplatform.library` and configures the Android side via `kotlin { android { … } }`, not a top-level `android {}` block.
- **Convention plugins (`build-logic`).** Standard shared KMP library modules don't repeat the toolchain/SDK/iOS-framework/compose/host-test boilerplate — they apply one or more **composable** convention plugins from the `build-logic` **included build** (wired via `includeBuild("build-logic")` in `settings.gradle.kts` `pluginManagement`). Plugin application is idempotent, so a module can apply several and the shared base still applies once:
  - **`frnk.kmp.base`** (core) — the KMP + AGP-KMP-library plugins, `jvmToolchain(17)`, and `compileSdk`/`minSdk` (from the catalog). **No iOS targets / no framework**, so it also serves the special modules with a non-standard iOS shape: `:demo-shared` (custom `XCFramework("DemoKit")`) applies `frnk.kmp.base` + its own framework shape, instead of hand-writing the toolchain/SDK.
  - **`frnk.kmp.library`** — `frnk.kmp.base` + bare `iosArm64()`/`iosSimulatorArm64()` targets (**no per-module framework** since restructure Stage 1/OQ-3 — iOS consumption is umbrella-only: `DemoKit` for the demo, each host's own framework otherwise). The default for standard shared library modules.
  - **`frnk.kmp.library.compose`** — `frnk.kmp.library` + the Compose plugin pair (`compose.multiplatform` + `kotlin.compose`) **+ `api(compose.runtime/foundation/ui)`** (so every Compose module exports them uniformly). Applied by `:ui-theme`, `:haptics`, `:ui-bottom-nav`, `:shared-monetization-ui` (and, via `.composehosttest`, `:ui-components`/`:ui-scaffolds`).
  - **`frnk.kmp.library.hosttest`** — `frnk.kmp.library` + `withHostTest {}` + the `commonTest` `kotlin-test`/`kotlinx-coroutines-test` deps. Applied by every standard tested module **except** `:ui-components`/`:ui-scaffolds` (they need the Compose-UI-test variant — see `.composehosttest` below).
  - **`frnk.kmp.library.composehosttest`** (restructure Stage 7b) — `frnk.kmp.library.compose` + the design-system test/preview wiring `:ui-components` and `:ui-scaffolds` share: `withHostTest { isIncludeAndroidResources = true }`, the `androidHostTest` bundle (`kotlin-test`/`coroutines-test`/`compose-ui-test`/`ui-test-manifest`/`robolectric`), and a `commonDebug` `@Preview` source set wired `dependsOn` androidMain + both iOS source sets (`compose-ui-tooling-preview`/`compose-ui-tooling`). Extracted from `:shared-ui-atoms`' former hand-written build.
  
  - **`frnk.android.firebase`** — the one convention plugin aimed at a **host application** rather
    than a toolkit module, and the only one a downstream app applies. On a `com.android.application`
    project it applies `google-services` (so `FirebaseInitProvider` auto-inits Firebase before
    `Application.onCreate`) and `firebase-crashlytics` (so R8-minified release stack traces
    deobfuscate), **conditionally on the host's `google-services.json` being present** — CI and fresh
    clones configure and build without it, and the `runCatching`-wrapped bindings in
    `:analytics-impl` degrade to a logged no-op at runtime. The host passes nothing and there is
    nothing to tune: Crashlytics collection defaults to on for every build type, and mapping upload
    defaults to on wherever a mapping exists (release only — debug isn't minified, so the upload
    task is never created). Consuming it needs `pluginManagement { includeBuild("frnk/build-logic") }`
    in the host's `settings.gradle.kts`; see `docs/HOST_INTEGRATION.md`. This is why `build-logic`
    carries the `google-services` + `firebase-crashlytics` plugin **markers**.

  (The old `frnk.backend.*` wrappers were retired at restructure Stage 5/OQ-6 — `:analytics-api`/`:analytics-impl` apply the standard plugins above and declare their namespaces/deps inline.)
  
  Each module then only declares what is specific to that module. **`build-logic` (not `buildSrc`) hosts the plugins** so their classpath attaches only to applying projects — a `buildSrc` would leak onto every project and clash with `alias(...) apply false`. **There is no `buildSrc` anymore** — it was deleted once its lone remaining constant (the Maven group id) moved into the version catalog (below); `build-logic` is now the single home for shared build logic. The remaining special module (`:demo-android` — `com.android.application`) keeps a hand-written build.
- `:demo-android` (the only `com.android.application`) uses AGP 9's **built-in Kotlin** — it does **not** apply `kotlin.android`. Don't re-add that plugin.
- Shared **non-SDK** constants live in **`gradle/libs.versions.toml`** alongside the SDK levels — there is no `buildSrc`/`ProjectConfiguration.kt` (deleted; the old `FrnkDB` database constants had already died at restructure Stage 4 — the toolkit owns no schema; the demo's `DemoDB` is configured inline in `demo/shared/build.gradle.kts`). The `dev.jdgarita.frnk` group id is the catalog `[versions]` entry **`frnk-groupId`**, read by the `frnk.kmp.base` convention plugin (`group =`) **and** by every module build script for its `namespace` (`libs.versions.frnk.groupId.get()`). The catalog lives here because it is the one source visible to **both** the `build-logic` included build and the module build scripts — buildSrc was visible only to the latter, which is exactly why the group id had to be duplicated before. **SDK floor/ceiling** — `android-minSdk`/`android-compileSdk`/`android-targetSdk` — likewise live **only** in the catalog as the single source of truth, read by the `frnk.kmp.library` convention plugin, the special modules' build scripts (`libs.versions.android.compileSdk.get().toInt()`), and composite-build host apps. AGP 9 caps compileSdk at 36.

## Architecture you need to respect

**Directory layout vs Gradle paths.** Since restructure Stage 3, modules physically live at their final layered locations — `frnk/core/*`, `frnk/data/*`, `frnk/ui/*`, `frnk/capabilities/*`, plus `demo/{shared,android-app,ios-app}` — while keeping flat Gradle project names (`:shared-utils` → `frnk/core/util`, `:core-platform` → `frnk/core/platform`, `:ui-components` → `frnk/ui/components`, `:demo-shared` → `demo/shared`, …) via `projectDir` remaps in `settings.gradle.kts`. The Stage 9 coordinate flip renamed `:shared-ui-nav` → `:ui-bottom-nav`, `:shared-monetization-api` → `:monetization-api`, `:shared-monetization-revenuecat` → `:monetization-impl`, and deleted the src-less `:shared-ui-api` + `:shared-ui-atoms` facades (their successors are `:core-mvi`/`:core-nav`/`:haptics` and `:ui-theme`/`:ui-components`/`:ui-scaffolds`); Stage 10 renamed the demo projects `:shared-demo` → `:demo-shared` and `:androidDemoApp` → `:demo-android` (see `settings.gradle.kts` for the full name→dir map). Two legacy `shared-` Gradle names remain current and correct: `:shared-utils` and `:shared-monetization-ui`. The analytics pair is already at its final flat names since Stage 5 (`:analytics-api` at `frnk/capabilities/analytics-api`, `:analytics-impl` at `frnk/capabilities/analytics-impl`, accessors `projects.analyticsApi`/`projects.analyticsImpl`) — the old nested `:shared:backend:*` paths and the `:shared`/`:shared:backend` hull projects are gone.

**No aggregator — consumers depend on individual modules (restructure Stage 1).** The old `:shared`/`:androidApp`/`:iosApp` aggregators are gone. **`:core-di`** owns the bootstrap: `initializeFrnk(modules: List<Module>)` (+ the androidMain `initializeFrnk(context, modules)` overload, which also sets `DatabaseContext.application` + `androidContext(...)`) and the fail-fast `requireFrnkKoin()`. **`:ui-app`** owns **`FrnkApp(onSavedStateConfiguration, onNavigationModule)`** — the lower-level app root: it owns `FrnkTheme` + the `AppearanceController` dark/light + system-bar appearance + a single root `NavDisplay` seeded at `FrnkRootRoute.Onboarding`, and hands the nav graph to the host (`onSavedStateConfiguration` supplies `frnkRootNavConfig(...)`; `onNavigationModule(backStack)` returns a Koin `navigation<Route> { … }` module loaded via `loadKoinModules`). No batteries auto-wired — the host registers its own root destinations (onboarding / tab shell / paywall) and wires nested tab nav itself. It also exports `frnkUiModules()` (the SDK-free scaffold VM modules: appearance/home/settings/onboarding + `frnkNestedNavModule`). A fresh host is `initializeFrnk(context = this, modules = frnkUiModules() + databaseModule + prefsModule + …)` then `FrnkApp(onSavedStateConfiguration = { frnkRootNavConfig() }, onNavigationModule = { backStack -> myRootModule(backStack) })`. See `docs/HOST_INTEGRATION.md` §4 for the full module list.

**api/impl module split.** Each domain that pulls in a third-party SDK has two modules:

- `:analytics-api`, `:data-db-api` (the `SqlDriverFactory` SPI), `:data-prefs-api` (`KeyValueStore` + `Preference<T>`), `:monetization-api`, `:remote-config-api` (`RemoteConfigService` — read-only typed key→value + `fetchAndActivate`) — pure-interface, no Ktor / no SQLDelight driver / no RevenueCat / no Firebase. Domain code depends on these. (The old `shared-database-api` split into the two data api modules at restructure Stage 4; `NoteStore` moved to the demo, OQ-2.)
- `:analytics-impl`, `:data-db-impl` (platform SQL drivers), `:data-prefs-impl` (multiplatform-settings), `:monetization-impl`, `:remote-config-impl` (Firebase Remote Config) — concrete bindings exposed as Koin modules (`firebaseObservabilityModule`, `databaseModule`, `prefsModule`, `revenueCatModule`, `remoteConfigModule`).
- **Remote Config is its own capability pair (restructure Stage 11 / OQ-1), a sibling of `:analytics-*` kept separate from it** — it replaced the old generic Firestore-shaped `RemoteData` stub (deleted at Stage 11, with `FirestoreRemoteData` + `firebaseBackendModule`). **`:camera` + `:permissions`** (`frnk/capabilities/`) are api-only **scaffolds** from the same stage: interface + no-op default (`NoopCameraController`/`NoopPermissionController`) + Koin module (`cameraModule`/`permissionsModule`), **no impl yet** and no native cinterop — real implementations are future feature work. Their no-op defaults let hosts compile/run against the contract and keep the XCFrameworks clean.

The point is swap-ability and parallel compilation. **Do not** add a third-party SDK dependency to an `*-api` module, and do not import an `*-impl` package from toolkit code — impls are installed by the host's `initializeFrnk(modules = …)` list and resolved via Koin (the demo modules are the sanctioned exception; `DatabaseContext` itself lives in `:core-di`'s androidMain since Stage 4, with the data impls depending on it).

**Capability selection is an explicit Koin module list, not an enum.** The `BackendChoice`/`ObservabilityChoice`/`MonetizationChoice` axes and the old aggregator helper were retired at restructure Stage 1: hosts pass exactly the modules they want to `initializeFrnk(...)` (`firebaseObservabilityModule` XOR `noopObservabilityModule` — the latter now lives in `:analytics-api` — `remoteConfigModule` XOR `noopRemoteConfigModule`, `revenueCatModule` + `monetizationModule` + `paywallScaffoldModule`, `databaseModule`, `prefsModule`, …). Un-passed modules never appear in the graph.

**Observability is a separate axis from the backend.** Analytics + crash reporting are selected independently of the data backend — a local-only app can still ship Firebase telemetry. Install `noopObservabilityModule` (`:analytics-api`, over `Noop{Analytics,Crash}`) or `firebaseObservabilityModule` (`:analytics-impl`), never both.

**`IdentitySource` is the one contract every identity consumer shares.** Declared in `:identity-api`
(`suspend fun identify(id: String): AppResult<Unit, IdentityError>`), it is implemented by
`AnalyticsTracker` and `CrashReporter` (`:analytics-api`) **and** `EntitlementProvider` /
`EntitlementManager` (`:monetization-api`) — so telemetry and billing take the host's uid through
one identically-shaped call. That is the reason for the single cross-capability api→api edge
`analytics-api ← identity-api`. `DefaultSyncAuthUseCase` (`:monetization-api`) is the orchestrator:
it resolves the anonymous uid, fans it out to all three sinks, and emits the
`IdentitySynced`/`IdentitySyncFailed` funnel. **Only the billing sink gates** — the two observability
sinks are best-effort and their results are deliberately discarded, so an unconfigured Firebase
degrades telemetry instead of blocking the app. Don't "fix" that into a blocking check;
`DefaultSyncAuthUseCaseTest` pins it.

**`shared-utils` is the root.** It owns coroutines + datetime + `BuildKonfig`-generated config, plus `PlatformInfo` (the module's only `expect/actual`: OS name/version + device model) and `FeedbackEmail` (pure-Kotlin `mailto:` draft builder). `AppResult<D, E : AppError>` (sealed `Success`/`Failure`, with `CommonError` + `fold(...)`) lives here too — it is the toolkit-wide result envelope, so any `*-api` (backend, database, monetization) returns it without a sibling `*-api`→`*-api` dependency. Every `*-api` interface returns `AppResult` rather than throwing — preserve this when adding new interfaces, because callers rely on exhaustive `when` for error handling.

**`shared-ui-api` was split at restructure Stage 6** into **`:core-mvi`** + **`:core-nav`** + **`:haptics`**; the src-less `:shared-ui-api` **facade** (`frnk/core/ui-api-facade`) that re-exported all three was deleted at the Stage 9 coordinate flip — consumers depend on the three successors directly. **`:core-mvi`** owns the MVI engine: `MviContract` (`UiState` / `UiIntent` / `UiEffect` / `ModelState` / `Arguments` markers), the model-first `MviViewModel<A, M, S, I, E>(factory)` (data-only `ModelState` mutated via `updateModel`, derived `UiState` via `mapToUiState`, runtime `Arguments` at `attach`/`onAttached`; intent SharedFlow + effect Channel; `CommonUiIntent`/`CommonUiEffect` for shared back handling), and `UiText`. **`:core-nav`** owns the **type-safe Navigation3 contract** (`ui/nav/`): `FrnkTabRoute` (a `@Serializable sealed interface FrnkTabRoute : NavKey` catalogue of default routes), the back-stack helpers (`NavBackStack<NavKey>.navigateTo`/`back`/`clearAndNavigateTo`), the `FrnkPendingRouteRequest` deep-link signal, the **symmetric** `SavedStateConfiguration` builders (`frnkRootNavConfig(hostRoutes)` for the root `FrnkRootRoute` stack + `frnkNestedNavConfig(hostRoutes)` for a nested/tab `FrnkTabRoute` stack — both take a host-routes module, replacing the removed single `frnkNavConfiguration`), and `FrnkRootRoute` (the parallel root-level catalogue for the lower-level `FrnkApp` path, coexisting with `FrnkTabRoute`). **No Compose deps in either** — the nav3 *runtime* is pure Kotlin/MP, so feature ViewModels (and MVI nav-effect handlers) compile without dragging in `compose.runtime`. Routes are `@Serializable` (`:core-nav` applies `kotlin-serialization` + depends on `kotlinx-serialization-core` — **core, not json**; nav3 encodes routes via savedstate's `SavedStateEncoder`) and depend on `androidx-navigation3-runtime` (`NavKey`/`NavBackStack`). New screens subclass `MviViewModel<A, M, S, I, E>`, mutate the data model in `updateModel { copy(...) }` (the `UiState` re-derives via the pure `mapToUiState`), and override `onIntent` for side-effectful work (using `emit(effect)` for one-shots). The **Compose bindings** for both engine and navigation — `FrnkScreen` (`ui/mvi/`) and `FrnkNavDisplay` + `rememberFrnkNavBackStack` + the slide animations (`ui/nav/`) — live up in **`:ui-scaffolds`** (since restructure Stage 7; they were in `:shared-ui-atoms`), since binding needs `compose.runtime`.

**`shared-ui-atoms` was split at restructure Stage 7** into **`:ui-theme`** (`frnk/ui/theme` — tokens `ui/tokens/*` + theme engine `ui/theme/*`: `FrnkTheme`/`FrnkThemeConfig`/`FrnkStrings`/`FrnkIcons`/`FrnkRipple`), **`:ui-components`** (`frnk/ui/components` — the dir `shared-ui-atoms` used to occupy; `ui/atoms/*` + `ui/molecules/*` + `ui/organisms/*` + `ui/placeholder/*`), and **`:ui-scaffolds`** (`frnk/ui/scaffolds` — `ui/scaffolds/*` + the Compose MVI bindings `ui/mvi/*` + the Compose nav bindings `ui/nav/*`). The multihaptic **engine** moved down into `:haptics` (Stage 7a). The src-less `:shared-ui-atoms` **facade** (`frnk/ui/atoms-facade`) that `api()`-re-exported `:ui-theme` + `:ui-components` + `:ui-scaffolds` (+ `:haptics`) was deleted at the Stage 9 coordinate flip; `:ui-bottom-nav` now depends on `:ui-scaffolds` directly. Dependency floor-to-ceiling: `haptics ← ui-theme ← ui-components ← ui-scaffolds ← ui-bottom-nav ← ui-app`. The design system (described below as one unit for orientation) now lives across those three modules:
- Headless Compose atoms built on `compose-unstyled` 2.x (the granular `com.composables:composeunstyled-{primitives,theming,platformtheme,button,icon,separators}` + `icons-lucide-cmp` artifacts; **not** `com.composables:core` and **not** Material3). The **only** sanctioned Material3 dependency in the whole toolkit lives in `:ui-bottom-nav` (see below) — it stays out of `:ui-theme`/`:ui-components`/`:ui-scaffolds` and every other module.
- Design tokens (`ui/tokens/`): `FrnkColors` (Light/Dark), `FrnkTypography`, `FrnkSpacing`, `FrnkShapes`, `FrnkIconSize`.
- Theme engine (`ui/theme/`): `FrnkTheme(config, content)` over `buildPlatformTheme`, with `ThemeProperty<T>`/`ThemeToken<T>` axes (colors, textStyles, shapes, strings, icons), animated light/dark palette via `LocalAppearanceController`, and `FrnkThemeConfig` as the single host-override entry point. `FrnkStrings`/`FrnkIcons` ship default registries that hosts override per-token. `FrnkTheme` also installs `LocalFrnkHaptics` (a `multihaptic`-backed `HapticFeedback`) so atoms vibrate on interaction with zero host wiring — same precedent as the ambient ripple.
- Haptics: the `top.ltfan.multihaptic` binding behind the Compose-free `HapticFeedback`/`HapticType` contract — **both contract and engine now live in `:haptics`** (the engine binding moved down from `:shared-ui-atoms` at restructure Stage 7a; `:ui-theme`'s `FrnkTheme` installs `LocalFrnkHaptics`). `LocalFrnkHaptics.current.perform(HapticType.Success)` is the host-facing one-liner; `rememberFrnkHaptics()` resolves the platform `Vibrator` (no Context plumbing); interactive atoms call `perform(...)` on press, gated by the enabled flag the Settings "Haptic feedback" toggle drives. Treated as a UI-feedback concern (like the ripple), **not** an api/impl backend split. No native cinterop, so the XCFrameworks stay clean.
- Atoms (`ui/atoms/`): `FrnkText`, `FrnkButton`, `FrnkIcon`, `FrnkIconButton`, `FrnkDivider`, `FrnkSwitch`, `FrnkSegmentedControl`, `FrnkTopAppBar` (status-bar-safe, with a search mode). Each takes an `@Immutable *State` class and separate callback lambdas; styling resolves from `Theme[colors][...]` / `Theme[textStyles][...]`.
- Molecules (`ui/molecules/`, P4-1 — small compositions of atoms + tokens, above atoms / below scaffolds): `FrnkListRow` (title/subtitle/leading-icon/trailing-slot row, optional whole-row `onClick`, optional swipe via `FrnkSwipeable`), `FrnkLabeledValue` (label + value, inline/stacked), `FrnkEmptyState` (icon/title/subtitle + optional CTA), and `FrnkSwipeable` (+ `FrnkSwipeAction`/`FrnkSwipeController`) — a generic swipe-to-action primitive (Dismiss/Reveal behaviors) usable around any content, a **headless, Material3-free** reimplementation. Same rules as atoms (`@Immutable *State`, callbacks before `modifier`, tokens-only, recorded skeleton decision, automatic ripple/haptics).
- Organisms (`ui/organisms/`, P4-2 — self-contained UI *sections* composed from molecules + atoms, above molecules / below scaffolds): `FrnkListSection` (titled card of `FrnkListRow`s, per-row click + trailing slot), `FrnkProfileHeader` (avatar + name/subtitle + stat tiles). Both lean on the internal `FrnkSectionCard` chrome primitive (shared with the Settings scaffold). Same conventions as molecules; pure view code, previews only — no unit tests (P4-4 added Compose UI tests for the highest-value **atoms** only; molecules/organisms stay previews-only).
- Scaffolds (`ui/scaffolds/`, above atoms / below features): `OnboardingScreen`, `SettingsScreen`, `HomeScreen` (each VM-backed + a stateless `*Content`), plus `FrnkScreenScaffold` — the standard top-bar-over-edge-to-edge-scrollable-content template, with the top bar and the host's floating bottom bar pinned (always visible) while content scrolls underneath them. `HomeScreen` is the home-tab template: a pinned `FrnkTopAppBar` over a **scaffold-owned** scrolling `Column` the host fills through a `ColumnScope` `content` slot (merged padding applied for it; hosts needing `LazyColumn` drop to `FrnkScreenScaffold`); its pass-through `HomeViewModel` re-emits every interaction as a `HomeEffect`. `defaultSettingsState` (composition-free; takes `hapticsEnabled`) accepts `extraSections` + `extraSectionsPlacement` (`AfterAppearance`/`BeforeSubscription`/`BeforeLegal` default/`End`) so hosts inject custom Settings sections without hand-building the state. `FeedbackEmailLauncher` opens the platform mail composer through `shared-utils`' `FeedbackEmail` + `PlatformInfo`.
- Bottom bar: the adaptive bar is a **fixed three-tab** shape — `Home · <custom> · Settings` — where Home and Settings are toolkit-fixed (labels, theme icon tokens, SF-Symbols, routes `FrnkTabRoute.Home` / `FrnkTabRoute.Settings`) and the **middle tab is host-provided** via `customTab: FrnkCustomTab`, all assembled inside `FrnkNestedNavScaffold`. The host supplies only `customTab` + the nested-nav Koin module registering the destinations behind the three routes; selection state **and the per-tab back stacks** live in the MVI `FrnkNestedNavViewModel`, not in `remember`. The old dynamic primary-action / FAB / Mode-B machinery (`FrnkPrimaryActionRegistry`/`FrnkPrimaryActionHandler`/`onPrimaryAction`/`FrnkNavPrimaryAction`) was removed.
- `@Preview` composables live in a dedicated `commonDebug` source set (`src/commonDebug/kotlin/.../previews/`) attached as `dependsOn` parent of `androidMain` + both iOS source sets, so previews compile cross-platform. AGP-9-KMP single-compilation caveat: `commonDebug` also ends up in release AARs today (inert composables, R8 strips); promote to a sibling module if true exclusion becomes load-bearing.

**`ui-bottom-nav` is the platform-adaptive bottom navigation — and the toolkit's SOLE Material3 dependency.** It owns `FrnkBottomFloatingBar` — an **`expect`/`actual` composable**: a Material3 *Expressive* `HorizontalFloatingToolbar` (floating pill) on Android (drawing `ImageVector` icons directly), and a native glassy `UITabBar` (iOS 26+) / Material3 bar (older) on iOS built on the toolkit's **vendored** `AdaptiveNavigationBar` (under `ui.bottomnav.vendor`, adapted from [narendraanjana09/adaptive-nav-bar](https://github.com/narendraanjana09/adaptive-navigation-bar); driven by SF-Symbol strings). Both are themed from `FrnkTheme` tokens. It also owns **`FrnkNestedNavScaffold(customTab, onNestedNavigationModule)`** (replaced the removed `FrnkTabbedNavScaffold`) — the toolkit's **FIXED three-tab** (`Home · <custom> · Settings`) **multiple-back-stack** tabbed scaffold. Home and Settings are toolkit-fixed (labels, theme icon tokens `iconNavHome`/`iconNavSettings`, SF-Symbols `"house"`/`"gearshape"`, routes `FrnkTabRoute.Home` / `FrnkTabRoute.Settings`); the **middle tab is host-provided** via **`customTab: FrnkCustomTab(route, icon, iosSystemIcon, label)`**. The host supplies only `customTab` + `onNestedNavigationModule` (the Koin module registering the destinations behind the three routes — `FrnkTabRoute.Home` / `customTab.route` / `FrnkTabRoute.Settings`). It is backed by the MVI **`FrnkNestedNavViewModel`** (registered by **`frnkNestedNavModule`**), which owns the bar's view state (`items` + `selectedIndex`) **and the per-tab back stacks** — selection lives in the VM, not in `remember`. The VM holds a single live `backStack` (rendered + handed to the host module, seeded with `FrnkTabRoute.Home`) plus per-tab snapshots; a tap → `FrnkNestedNavIntent.Tap(index)` → the VM switches the active tab (snapshotting the outgoing stack, swapping in the target's), and re-tapping the active tab pops it to root. System/predictive back at a tab root from a non-Home tab → `FrnkNestedNavIntent.Back` → returns to Home. It renders `FrnkNavDisplay` + the persistent `FrnkBottomFloatingBar` overlay + a **conditional** `BackHandler` (only at a single-entry tab stack on a non-Home tab; within-tab pops are left to `NavDisplay`) + `LocalFrnkBottomBarInset` bookkeeping. **Per-tab back stacks are in-memory** (survive recomposition + config change, not full process death — `onSavedStateConfiguration` was removed); full-screen bar hiding is not yet implemented. **Icons:** Home/Settings use theme icon tokens via `FrnkIconSource.Token(iconNavHome/iconNavSettings)` (resolved to an `ImageVector` on Android via `.resolve()`) **+** an `iosSystemIcon: String` (`"house"`/`"gearshape"`); the middle tab's icon + SF-Symbol come from `customTab` (which may pass a `FrnkIconSource.Vector` for a host-owned icon) — **no `DrawableResource` in the API.** Material3 is **split by source set** (material3 `1.10.0-alpha05` in `androidMain` for the `HorizontalFloatingToolbar`; the vendored bar + material3 in `iosMain`) but stays inside this one module's `build.gradle.kts`, so `:ui-components`/`:ui-theme`/`:ui-scaffolds` stay `compose-unstyled`-only. Material3 reaches every consumer of this module (and of `:ui-app` above it) — a deliberate, host-approved trade. Pure Kotlin/Compose (no extra native cinterop), so the XCFramework still links under the consumer's `dynamic_lookup`. **History:** Calf was the original iOS engine (removed when adaptive-nav-bar became default); then the Android engine was swapped from adaptive-nav-bar's Material3 `NavigationBar` to the Expressive `HorizontalFloatingToolbar` and the API moved off `DrawableResource` to `ImageVector` — which **also removed the old Android raw-asset host step** (Android no longer reads any `DrawableResource`; the iOS-only library shim uses a bundled placeholder); the iOS bar was later **vendored** into `ui.bottomnav.vendor`; the primary-action FAB was first retired for a centered bar item (Mode B), then the whole dynamic primary-action mechanism was dropped; the later fixed three-tab `FrnkTabbedNavScaffold` was in turn replaced by the host-driven `FrnkNestedNavScaffold`. `FrnkBottomFloatingBar` is the toolkit's **sole** bottom-nav bar — the old Material-free `FrnkBottomNavBar` pill atom + its `BottomNavScaffold` were removed (no host or demo used them). **Do not add Material3 to any other module.**

**`shared-monetization-ui` is the frnk-owned paywall + subscription-management UI** (above `:monetization-api`, no RevenueCat dependency itself): the `PaywallScreen`/`PaywallViewModel` MVI screen wired through `frnkPaywallDestination(...)` (a `NavGraphBuilder` extension) + `paywallScaffoldModule` (Koin), and the host-facing `rememberFrnkSettingsHandler()` (backed by an internal `platformManageSubscriptionsUrl()` `expect/actual` that supplies the platform's native subscription-management URL to open). The demo and `:ui-app` both consume it; it's the toolkit's monetization *view* layer, distinct from the api/impl backend split.

**Public entry points are the individual modules.** Android hosts depend on the `dev.jdgarita.frnk:<module>` coordinates they use (composite-build substitution matches by name); iOS hosts build their own umbrella XCFramework exporting those modules (see `docs/HOST_INTEGRATION.md` §6). There is no prebuilt toolkit framework.

**`:demo-shared` is demo-only.** A KMP module that owns the cross-platform `FrnkDemoApp` composable (the unified entry point both platforms call, calling `:ui-app`'s `FrnkApp` — mounting `FrnkNestedNavScaffold` at the `FrnkRootRoute.Tab` destination and wiring its own paywall/onboarding), `DemoViewModel` (MVI), `demoModule` (Koin bindings with `FakeEntitlementProvider` + the frnk `monetizationModule`/`paywallScaffoldModule` + `FakeKeyValueStore` + logging fakes), and an iOS `MainViewController()` factory that Swift mounts via `UIViewControllerRepresentable`. It produces its own `DemoKit.xcframework`. Critically, `:demo-shared` depends only on the `*-api` modules + `:ui-theme`/`:ui-components`/`:ui-scaffolds` (re-pointed from the `:shared-ui-atoms` facade at Stage 7, since Kotlin/Native `export` is non-transitive) + `:ui-bottom-nav` + `:shared-monetization-ui` + `:ui-app` (no `*-impl` in common — `:ui-app` itself carries none, so it's cinterop-safe) — so `DemoKit`'s **common** surface stays free of RevenueCat / SQLite native cinterops. **`iosMain` exceptions** add two native cinterops so the iOS demo exercises real paths (each supplied by `iosDemoApp` via SPM under `dynamic_lookup`): **CrashKiOS** (`co.touchlab.crashkios:crashlytics`, BACKLOG P1-5b) for the "Force crash" → Crashlytics test, and **RevenueCat** (`purchases-kmp`, BACKLOG P3-3) so `bootstrapDemoKoinWithRevenueCat(apiKey)` installs the real `revenueCatModule` over the fake provider against the RevenueCat **Test Store**. So `iosDemoApp` links the native **Firebase + RevenueCat** SDKs (via SPM) + ships `GoogleService-Info.plist` and no longer boots on a bare simulator. Both demos share `bootstrapDemoKoin()`; `demo-android` overrides with `firebaseObservabilityModule` + (when a key is set) `revenueCatModule`, and `iosDemoApp` uses `bootstrapDemoKoinWithRevenueCat(...)` (the iOS crash hook + `FirebaseApp.configure()` are wired separately in Swift). Production consumers never touch `:demo-shared`; they depend on the individual toolkit modules (own umbrella framework on iOS).

**iOS linker quirk.** Umbrella frameworks that bundle `:monetization-impl` (DemoKit; host frameworks) set `linkerOpts("-undefined", "dynamic_lookup")` because that module cinterops the native purchases-ios SDK — expected to be supplied by the consumer Xcode project via CocoaPods or SPM. Deferring symbol resolution lets the XCFramework link locally; the consumer app's own link step resolves the native RevenueCat/Firebase symbols at integration time.

## Ktlint runs locally, not in CI

`./build.gradle.kts` applies the ktlint plugin to **all** projects with `ignoreFailures.set(false)`. Style is enforced via a **git pre-commit hook** (`.githooks/pre-commit`) that runs `./gradlew ktlintFormat` and re-stages the fixed files — so commits land already-formatted and CI no longer needs a separate ktlint job.

The hook activates automatically: the root build registers an `installGitHooks` task that points `core.hooksPath` at `.githooks/`, and it's wired to `prepareKotlinBuildScriptModel` so IDE sync (or any `./gradlew` invocation that triggers it) installs the hook. To install manually: `./gradlew installGitHooks`. To bypass for one commit: `SKIP_KTLINT=1 git commit ...` or `git commit --no-verify`.

## CI

**Build/test CI is paused while the repo is private.** Free-tier GitHub Actions minutes are capped on private repos, and the per-push `compile & test` job was exhausting the spending limit. `main.yml` (build/test) and `claude-code-review.yml` (auto PR review) were **removed** for now. Two workflows remain, both cheap because they only run on rare/explicit triggers:

- **`release.yml`** — fires on a `v*` tag push: verifies `Frnk.VERSION` matches the tag, extracts the matching `CHANGELOG.md` section, and creates the GitHub Release (one `gh release create`). This is the "one CI job for tagging releases" we intentionally keep. See `docs/RELEASING.md`.
- **`claude.yml`** — on-demand `@claude` assistant on issues/PRs; consumes minutes only when explicitly mentioned.

**Validation is local until CI returns.** Before pushing, run the old gate yourself: `./gradlew compileAndroidMain :demo-android:compileDebugKotlin` then `./gradlew testAndroidHostTest :demo-android:testDebugUnitTest` (both `--parallel --build-cache`). `compileAndroidMain` covers `commonMain`+`androidMain` for every KMP module (the AGP 9 KMP-Android task name — `compileDebugKotlinAndroid` doesn't exist for KMP modules); `testAndroidHostTest` covers `commonTest`+`androidHostTest` for every module that opted in via `kotlin { android { withHostTest {} } }` (KMP modules have no `testDebugUnitTest`; `:demo-android`, a `com.android.application`, does). Style is enforced by the pre-commit hook (above), not CI.

**Branch protection and PRs are already back on `main`** — direct pushes are rejected and a PR needs one code-owner approval, which is why even a release-bookkeeping commit goes through a PR (`docs/RELEASING.md`). What is still pending: once the toolkit's foundation is in place and the repo goes public (unlimited Actions minutes), restore the `compile & test` job — and optionally `claude-code-review.yml`.

## Conventions to follow when adding code

- **Extension functions live in their own file under an `ext/` subpackage** of the module they belong to (e.g. `dev.jdgarita.frnk.ui.scaffolds.settings.ext`, `frnk/ui/scaffolds/src/commonMain/.../ui/scaffolds/settings/ext/SettingsModelStateExt.kt`), **not** appended to the type's declaration file. Name the file `<Type>Ext.kt` (the extensions on `SettingsModelState` → `SettingsModelStateExt.kt`). Keeps data-class/type files declaration-only and makes extensions discoverable. Applies to every new extension function going forward.
- New backend call: define the interface + DTOs in `:analytics-api`, add the concrete impl in `:analytics-impl`, register the binding in `FirebaseObservabilityModule.kt`. Return `AppResult`, never throw.
- New `ToolkitEvent`: the `key` must be alphanumeric-plus-underscore and start with a letter. Firebase Analytics rejects anything else (hyphens included) and **silently drops the event** — and `FirebaseAnalyticsTracker` wraps every SDK call in `runCatching`, so a malformed key fails invisibly with nothing in logcat. The vocabulary is lowercase `snake_case` (`app_opened`, `identity_synced`).
- New persisted entity: **the toolkit owns no schema** (restructure Stage 4 / OQ-2) — relational entities belong to the consuming app. The host (or `demo/shared` for demo scaffolding) applies the SQLDelight plugin, owns the `.sq` files + database class, and builds it through `:data-db-api`'s `SqlDriverFactory` (bound by `databaseModule` in `:data-db-impl`); see `docs/HOST_INTEGRATION.md` §1 and the demo's `DemoDB`/`demoNotesModule` as the worked example.
- New key-value preference: don't reach for raw `KeyValueStore` keys — use the typed `Preference<T>` layer in `:data-prefs-api` (`Preference.kt`, P4-3; coverage completed in Tier 3.4). `KeyValueStore.stringPreference/nullableStringPreference/booleanPreference/intPreference/longPreference/doublePreference/enumPreference(key, default)` return a `ReadWriteProperty`, so hosts write `var fooEnabled by store.booleanPreference("foo", false)`. Int/Long/Double/Enum encode losslessly over the String primitive (unknown/corrupt values fall back to the default; enum decode never throws); `nullableStringPreference` models `null` as key absence (writing `null` clears the key).
- New screen: state/intent/effect types + a `MviViewModel` subclass in the feature module (depend on `:core-mvi`/`:core-nav` if no Compose is needed, or `:ui-scaffolds` for the composable bindings / `:ui-components` for atoms). Compose the UI with `Frnk*` atoms under a `FrnkTheme { ... }`. Prefer the toolkit's binding primitive **`FrnkScreen(viewModel, arguments, onEffect = { … }) { state -> … }`** (in `:ui-scaffolds`, `ui/mvi/`) — it attaches the VM (calls `attach`), collects state lifecycle-aware, consumes one-shot effects via `onEffect`, and renders your `content(state)`; wrap that content in `FrnkScreenScaffold` for the standard top-bar template (as `FrnkHomeScreen` does). The effect channel is single-consumer — collect it in exactly one place.
- New navigation flow: the toolkit uses **AndroidX Navigation3**. Define `@Serializable` route types implementing `NavKey` (extend `FrnkTabRoute` or declare your own; the route-owning module needs the `kotlin-serialization` plugin). Build the saved-state config with **`frnkNestedNavConfig(hostRoutes = SerializersModule { polymorphic(NavKey::class) { subclass(…) } })`** (registers your routes alongside the toolkit's tab routes; use `frnkRootNavConfig(hostRoutes)` for the root `FrnkRootRoute` stack of the lower-level `FrnkApp` path — both replace the removed single `frnkNavConfiguration`), create the host-owned back stack with **`rememberFrnkNavBackStack(config, startRoute)`**, and render **`FrnkNavDisplay(backStack)`** (`:ui-scaffolds`, `ui/nav/`) — it bakes in the saveable-state + ViewModel-store entry decorators and the slide transitions. Register destinations either via Koin's `navigation<Route> { … }` DSL (the default `koinEntryProvider()`) or a local `entryProvider { entry<Route> { … } }`. Drive navigation as a **`UiEffect`**: a ViewModel emits it, a single effect collector (e.g. `FrnkScreen`'s `onEffect`) above the host mutates the back stack via `backStack.navigateTo(route)` / `back()` / `clearAndNavigateTo(route)` — collect in exactly one place (single-consumer channel). For a bottom-nav with **multiple back stacks**, mount **`FrnkNestedNavScaffold(customTab = FrnkCustomTab(route, icon, iosSystemIcon, label), onNestedNavigationModule = { backStack -> … })`** (`:ui-bottom-nav`): it renders the **fixed** `Home · <custom> · Settings` bar (Home + Settings toolkit-owned, the middle tab supplied via `customTab`), and you supply the destinations behind the three routes (`FrnkTabRoute.Home` / `customTab.route` / `FrnkTabRoute.Settings`) through `onNestedNavigationModule`. The scaffold owns the `FrnkNavDisplay` + persistent adaptive bar + VM-owned tab selection **and per-tab back stacks** (`FrnkNestedNavViewModel`, so `selectedIndex` and each tab's history survive recomposition rather than living in `remember`) + the bottom-inset (via `LocalFrnkBottomBarInset`, so screens on `FrnkScreenScaffold` reserve the bar automatically). Each tab keeps its own back stack (in-memory: survives recomposition + config change, not full process death); re-tapping the active tab pops it to root, and system back at a non-Home tab root returns to Home. For a finished flow use `clearAndNavigateTo(route)`. On Android `NavDisplay` auto-pops system/predictive back *within* a tab (host activity sets `android:enableOnBackInvokedCallback="true"`); on iOS also give pushed screens an on-screen back affordance. `:demo-shared`'s `FrnkDemoApp` is the reference integration; deep-link in via `FrnkPendingRouteRequest`.
- New host app spin-up: the highest-level path is **`FrnkApp(onSavedStateConfiguration = { frnkRootNavConfig() }, onNavigationModule = { backStack -> myRootModule(backStack) })`** (`:ui-app`) after `initializeFrnk(context = this, modules = frnkUiModules() + …)` (Android) / `initializeFrnk(modules = …)` (iOS, both in `:core-di`). `FrnkApp` owns `FrnkTheme` + the `AppearanceController` dark/light + system-bar appearance + a single root `NavDisplay` seeded at `FrnkRootRoute.Onboarding`, then hands the nav graph to the host: the host owns its root nav module registering the `FrnkRootRoute` destinations (Onboarding / Tab / Paywall) and mounts **`FrnkNestedNavScaffold`** (`:ui-bottom-nav`, `ui/bottomnav/`) at the `Tab` destination (it renders the fixed `Home · <custom> · Settings` bar — the host passes `customTab: FrnkCustomTab` for the middle tab and registers the destinations behind the three routes). Nothing is auto-mounted at the low level. For the common `onboarding → tab shell → paywall` shape, **`frnkTabbedRootModule(customTab) { home/custom/settings + optional onboarding/paywall }`** (`:ui-app`) builds that whole root graph from content slots — the slots get a `FrnkTabNavigator` (`open`/`back`/`openPaywall`/`showOnboarding`) and the helper wires the cross-level navigation + onboarding→Tab / paywall→back conventions; pair with `startRoute = rememberFrnkRootStartRoute()` for first-launch onboarding gating (the lower-level `FrnkApp(onNavigationModule)` stays for full control). `:demo-shared`'s `FrnkDemoApp` is the reference integration. See `docs/HOST_INTEGRATION.md` §8.
- **State hoisting over local state.** Screen / navigation / business state lives in the feature's `MviViewModel` (`*State` + `*Intent`), never as `var … by remember { mutableStateOf(…) }` inside a composable. Composables stay stateless: read from the collected `state`, emit `onIntent(...)`. Reserve `remember` / `rememberSaveable` for genuinely-local UI holders (scroll / pager / focus / animation state, and `remember`-derived builders like `rememberFrnkNavController`). The atoms and scaffolds already follow this — match them.
- New atom: live under `frnk/ui/components/src/commonMain/.../ui/atoms/`. Model its `*State` as a **`sealed interface` with a `Content` data class + a `data object Skeleton`** (add an `Error` data class where there's a real error visual) — this is the toolkit's mandated state shape (see `docs/HOST_INTEGRATION.md` §9 — "Component style guide"). The composable takes `state` + callbacks + `modifier` and `when`-switches on the sealed state. Read styling from `Theme[colors][...]` / `Theme[textStyles][...]` and spacing/sizes from `Theme[spacing][...]` / `Theme[iconSizes][...]`, never hardcoded `Color(0xFF...)` or raw `.dp`. Add a `@Preview` to `src/commonDebug/.../previews/` using `PreviewSurface(appearance = ...)`. **Always ask whether the atom needs a loading skeleton.** If yes (most content-bearing atoms do), the `Skeleton` branch renders a **non-interactive** placeholder via `Modifier.frnkSkeleton(FrnkSkeleton(enabled = true), shape = <the atom's natural shape token>)` (no clickable/toggleable node) while `Content` renders the real UI; if the atom paints a brand color, the `Skeleton` branch simply doesn't paint it (no fill to peek through). Showcase the `Skeleton` state in the demo + a `@Preview`. If a skeleton genuinely doesn't apply (e.g. a pure divider, a terminal empty state), keep the state non-sealed / skip the object and say why. (`FrnkText` is the documented exception that also keeps a per-subtype `skeleton` field for content-sized text skeletons.) **Press feedback is automatic**: `FrnkTheme` installs a ripple as `LocalIndication`, so any atom built on `UnstyledButton` / `Modifier.clickable` / `selectable` / `toggleable` ripples with no extra wiring — don't pass an `indication` unless you deliberately want a different one. Host apps apply the same ripple to their own components via `rememberFrnkRipple()`. **Haptics are automatic too**: interactive atoms call `LocalFrnkHaptics.current.perform(HapticType.Click)` (buttons) or `.perform(HapticType.Selection)` (toggles/selectors) on interaction, gated by the global enabled flag — wire new interactive atoms the same way rather than hand-rolling vibration.
- New molecule / organism (compositions between atoms and scaffolds): molecules live under `frnk/ui/components/src/commonMain/.../ui/molecules/`, organisms under `.../ui/organisms/`. Same rules as atoms — `@Immutable *State`, callbacks before `modifier`, tokens-only styling, automatic ripple/haptics (don't re-wire), a `@Preview` in the matching `commonDebug/.../previews/` package, and a recorded skeleton decision. They're pure view code, previews only — no unit tests (P4-4 added Compose UI tests for the highest-value **atoms** only; molecules/organisms stay previews-only). Reuse the **public** `FrnkSectionCard` (in `:ui-components` `ui/organisms/`; promoted from `internal` at Stage 7b since the Settings scaffold now consumes it cross-module from `:ui-scaffolds`) for titled-card chrome rather than re-rolling it.
- New adaptive-nav surface: goes in `:ui-bottom-nav` (`ui/bottomnav/`) — the **only** module allowed a Material3 dependency. Don't add Material3 anywhere else.
- New scaffold (fixed-shape page template above atoms, below features): live in `:ui-scaffolds` under `frnk/ui/scaffolds/src/commonMain/.../ui/scaffolds/`, each scaffold in **its own subpackage** (`ui.scaffolds.{home,onboarding,settings}`; reducer helpers extracted to a `<feature>/ext/` file per the ext-function convention — e.g. `settings/ext/SettingsScreenStateExt.kt`). Expose a **VM-backed convenience composable** that resolves an `MviViewModel` via `koinViewModel { parametersOf(initialState) }`, backed by a stateless `internal fun *Content(state, onIntent, modifier)` renderer (previews + the wrapper only — keep it `internal`, not host API, unless an out-of-module consumer truly needs it). Register the VM in a per-scaffold Koin module (`xxxScaffoldModule`) that downstream Koin modules `includes(...)`. Default copy goes through `FrnkStrings` so hosts can override per-token.
- New tests: write **platform-agnostic** ones (reducers, `*-api` logic) in the module's `commonMain`-sibling `commonTest` source set; tests that need a platform-only runtime go in `androidHostTest` instead (Compose UI + Robolectric in `:ui-components`/`:ui-scaffolds`, the JDBC driver in `demo/shared`'s NoteStore round-trip). Note `:ui-components`/`:ui-scaffolds` have **no** `commonTest` source set — their tests are all `androidHostTest` (both apply the `frnk.kmp.library.composehosttest` convention plugin, which supplies the `withHostTest{isIncludeAndroidResources}` + Robolectric bundle + the `commonDebug` preview wiring). A KMP module only gets a host unit-test compilation after opting in with `kotlin { android { withHostTest {} } }` and adding `commonTest.dependencies { implementation(libs.kotlin.test); implementation(libs.kotlinx.coroutines.test) }`; the task is **`testAndroidHostTest`** (not `testDebugUnitTest`). Reducer tests follow `MviViewModelTest` in `:core-mvi` (set `Dispatchers.setMain` since `viewModelScope` drives the intent collector); fakes for `*-api` interfaces follow `FakeAnalyticsTracker` in `:analytics-api` `commonTest`. Reducers and `*-api` logic should land with tests. **Compose UI tests for the design system are the exception** (P4-4): they need a real composition + Robolectric, which have no common/iOS variant, so they live in `:ui-components`'s (atoms) / `:ui-scaffolds`'s (scaffolds) **`androidHostTest`** source set (not `commonTest`) and extend `RobolectricComposeTest` — they still run on `testAndroidHostTest`. See `frnk/ui/components/CLAUDE.md` + `frnk/ui/scaffolds/CLAUDE.md`.
- iOS-visible API surface: anything Swift needs to call must be in a module the consumer's umbrella framework `export(...)`s (for the demo: `:demo-shared`'s `DemoKit` export list).
- **Every new feature is demoed in all three demo layers.** A feature isn't done until it's exercised in `:demo-shared` (cross-platform), `demo-android` (installs and runs on a device/emulator), and `iosDemoApp` (builds the `DemoKit.xcframework` and runs in a simulator). If a feature genuinely can't be demoed (e.g., a build-time-only refactor), say so explicitly and explain why.

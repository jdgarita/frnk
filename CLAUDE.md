# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`frnk` is a Kotlin Multiplatform + Compose Multiplatform **toolkit** (not a standalone app) intended to be consumed by downstream apps as a Git submodule via a Gradle composite build (`includeBuild("../frnk")`). The `demo/` directory (`demo/android-app`, `demo/ios-app`, `demo/shared`) exists only as internal smoke harnesses — they are not the shipping product.

Read `docs/ARCHITECTURE.md` first when reasoning about cross-module changes; it is the canonical description of the module graph and the api/impl split.

## Common commands

Bootstrap (one-time per checkout):
```bash
cp local.properties.template local.properties   # then fill in Firebase keys; BuildKonfig reads from this
```

Day-to-day:
```bash
./gradlew compileAndroidMain                # fast compile-only check (what CI runs — covers commonMain+androidMain for every KMP module); Gradle parallelises across modules
./gradlew testAndroidHostTest               # commonTest + androidHostTest across all KMP modules (what CI runs); :androidDemoApp uses testDebugUnitTest
./gradlew :data-prefs-api:testAndroidHostTest   # run a single module's tests
./gradlew ktlintFormat                      # auto-fix style (also runs from the pre-commit hook)
./gradlew assemble                          # full build of every target — only when producing release artifacts
./gradlew :shared-demo:assembleDemoKitDebugXCFramework  # produce demo/shared/build/XCFrameworks/debug/DemoKit.xcframework (demo/ios-app consumes this)
./gradlew clean
```

`local.properties` is gitignored and required — `BuildKonfig` will fail at configuration time without `FIREBASE_*` and `BUILD_VARIANT`.

`iosDemoApp` needs local setup beyond `local.properties`: drop in its own `GoogleService-Info.plist` and let Xcode resolve Swift packages on first open (Firebase SDK). Both are gitignored — `GoogleService-Info.plist` and the Xcode-managed `**/xcshareddata/swiftpm/Package.resolved` — so a fresh checkout of the demo isn't buildable from CI (which never builds iOS anyway); it's a local-only harness.

## Toolchain pinning (don't fight it)

- **JDK 17** everywhere. Android Studio bundles JDK 21; the Foojay resolver in `settings.gradle.kts` auto-provisions 17, and the `frnk.kmp.library` convention plugin calls `kotlin { jvmToolchain(17) }` for every standard module because AGP's javac and the Kotlin task would otherwise disagree about target. Don't change this without changing both sides.
- **Kotlin 2.4.0 + AGP 9.2.1 + Gradle 9.5.1.** AGP 9 forbids combining `org.jetbrains.kotlin.multiplatform` with `com.android.library` in the same subproject — every KMP-Android module here applies `com.android.kotlin.multiplatform.library` and configures the Android side via `kotlin { android { … } }`, not a top-level `android {}` block.
- **Convention plugins (`build-logic`).** Standard shared KMP library modules don't repeat the toolchain/SDK/iOS-framework/compose/host-test boilerplate — they apply one or more **composable** convention plugins from the `build-logic` **included build** (wired via `includeBuild("build-logic")` in `settings.gradle.kts` `pluginManagement`). Plugin application is idempotent, so a module can apply several and the shared base still applies once:
  - **`frnk.kmp.base`** (core) — the KMP + AGP-KMP-library plugins, `jvmToolchain(17)`, and `compileSdk`/`minSdk` (from the catalog). **No iOS targets / no framework**, so it also serves the special modules with a non-standard iOS shape: `:shared-demo` (custom `XCFramework("DemoKit")`) applies `frnk.kmp.base` + its own framework shape, instead of hand-writing the toolchain/SDK.
  - **`frnk.kmp.library`** — `frnk.kmp.base` + bare `iosArm64()`/`iosSimulatorArm64()` targets (**no per-module framework** since restructure Stage 1/OQ-3 — iOS consumption is umbrella-only: `DemoKit` for the demo, each host's own framework otherwise). The default for standard shared library modules.
  - **`frnk.kmp.library.compose`** — `frnk.kmp.library` + the Compose plugin pair (`compose.multiplatform` + `kotlin.compose`) **+ `api(compose.runtime/foundation/ui)`** (so every Compose module exports them uniformly). Applied by `:ui-theme`, `:haptics`, `:shared-ui-nav`, `:shared-monetization-ui` (and, via `.composehosttest`, `:ui-components`/`:ui-scaffolds`).
  - **`frnk.kmp.library.hosttest`** — `frnk.kmp.library` + `withHostTest {}` + the `commonTest` `kotlin-test`/`kotlinx-coroutines-test` deps. Applied by every standard tested module **except** `:ui-components`/`:ui-scaffolds` (they need the Compose-UI-test variant — see `.composehosttest` below).
  - **`frnk.kmp.library.composehosttest`** (restructure Stage 7b) — `frnk.kmp.library.compose` + the design-system test/preview wiring `:ui-components` and `:ui-scaffolds` share: `withHostTest { isIncludeAndroidResources = true }`, the `androidHostTest` bundle (`kotlin-test`/`coroutines-test`/`compose-ui-test`/`ui-test-manifest`/`robolectric`), and a `commonDebug` `@Preview` source set wired `dependsOn` androidMain + both iOS source sets (`compose-ui-tooling-preview`/`compose-ui-tooling`). Extracted from `:shared-ui-atoms`' former hand-written build.
  
  (The old `frnk.backend.*` wrappers were retired at restructure Stage 5/OQ-6 — `:analytics-api`/`:analytics-impl` apply the standard plugins above and declare their namespaces/deps inline.)
  
  Each module then only declares what is specific to that module. **`build-logic` (not `buildSrc`) hosts the plugins** so their classpath attaches only to applying projects — `buildSrc` would leak onto every project and clash with `alias(...) apply false`. The remaining special module (`:androidDemoApp` — `com.android.application`) keeps a hand-written build.
- `:androidDemoApp` (the only `com.android.application`) uses AGP 9's **built-in Kotlin** — it does **not** apply `kotlin.android`. Don't re-add that plugin.
- Shared **non-SDK** constants (the `dev.jdgarita.frnk` group id) live in `buildSrc/src/main/kotlin/ProjectConfiguration.kt` (the old `FrnkDB` database constants died at restructure Stage 4 — the toolkit owns no schema; the demo's `DemoDB` is configured inline in `demo/shared/build.gradle.kts`). **SDK floor/ceiling are NOT there** — `android-minSdk`/`android-compileSdk`/`android-targetSdk` live **only** in `gradle/libs.versions.toml` as the single source of truth, read by the `frnk.kmp.library` convention plugin, the special modules' build scripts (`libs.versions.android.compileSdk.get().toInt()`), and composite-build host apps. AGP 9 caps compileSdk at 36.

## Architecture you need to respect

**Directory layout vs Gradle paths.** Since restructure Stage 3, modules physically live at their final layered locations — `frnk/core/*`, `frnk/data/*`, `frnk/ui/*`, `frnk/capabilities/*`, plus `demo/{shared,android-app,ios-app}` — while keeping their **current** Gradle project names (`:shared-utils` → `frnk/core/util`, `:ui-components` → `frnk/ui/components`, the `:shared-ui-atoms` facade → `frnk/ui/atoms-facade`, `:shared-demo` → `demo/shared`, …) via `projectDir` remaps in `settings.gradle.kts`. The remaining project renames come later (Stages 9/10; see `docs/RESTRUCTURE_PLAN.md` §3 for the full map). The analytics pair is already at its final flat names since Stage 5 (`:analytics-api` at `frnk/capabilities/analytics-api`, `:analytics-impl` at `frnk/capabilities/analytics-impl`, accessors `projects.analyticsApi`/`projects.analyticsImpl`) — the old nested `:shared:backend:*` paths and the `:shared`/`:shared:backend` hull projects are gone.

**No aggregator — consumers depend on individual modules (restructure Stage 1).** The old `:shared`/`:androidApp`/`:iosApp` aggregators are gone. **`:core-di`** owns the bootstrap: `initializeFrnk(modules: List<Module>)` (+ the androidMain `initializeFrnk(context, modules)` overload, which also sets `DatabaseContext.application` + `androidContext(...)`) and the fail-fast `requireFrnkKoin()`. **`:ui-app`** owns **`FrnkAppScaffold`** — the batteries-included app root over `:shared-ui-nav`'s `FrnkAppShell` (Koin fail-fast assertion, live `EntitlementManager.isPro`-driven Settings, `rememberFrnkSettingsHandler` wiring, auto-mounted `ToolkitRoute.Paywall`) — plus `frnkUiModules()` (the SDK-free scaffold VM modules). A fresh host is `initializeFrnk(context = this, modules = frnkUiModules() + databaseModule + prefsModule + …)` + `FrnkAppScaffold(appName, appVersion) { /* home items */ }`. See `docs/HOST_INTEGRATION.md` §4 for the full module list.

**api/impl module split.** Each domain that pulls in a third-party SDK has two modules:

- `:analytics-api`, `:data-db-api` (the `SqlDriverFactory` SPI), `:data-prefs-api` (`KeyValueStore` + `Preference<T>`), `shared-monetization-api` — pure-interface, no Ktor / no SQLDelight driver / no RevenueCat. Domain code depends on these. (The old `shared-database-api` split into the two data api modules at restructure Stage 4; `NoteStore` moved to the demo, OQ-2.)
- `:analytics-impl`, `:data-db-impl` (platform SQL drivers), `:data-prefs-impl` (multiplatform-settings), `shared-monetization-revenuecat` — concrete bindings exposed as Koin modules (`firebaseBackendModule`, `databaseModule`, `prefsModule`, `revenueCatModule`).

The point is swap-ability and parallel compilation. **Do not** add a third-party SDK dependency to an `*-api` module, and do not import an `*-impl` package from toolkit code — impls are installed by the host's `initializeFrnk(modules = …)` list and resolved via Koin (the demo modules are the sanctioned exception; `DatabaseContext` itself lives in `:core-di`'s androidMain since Stage 4, with the data impls depending on it).

**Capability selection is an explicit Koin module list, not an enum.** The `BackendChoice`/`ObservabilityChoice`/`MonetizationChoice` axes and the old aggregator helper were retired at restructure Stage 1: hosts pass exactly the modules they want to `initializeFrnk(...)` (`firebaseBackendModule`, `firebaseObservabilityModule` XOR `noopObservabilityModule` — the latter now lives in `:analytics-api` — `revenueCatModule` + `monetizationModule` + `paywallScaffoldModule`, `databaseModule`, `prefsModule`, …). Un-passed modules never appear in the graph.

**Observability is a separate axis from the backend.** Analytics + crash reporting are selected independently of the data backend — a local-only app can still ship Firebase telemetry. Install `noopObservabilityModule` (`:analytics-api`, over `Noop{Analytics,Crash}`) or `firebaseObservabilityModule` (`:analytics-impl`), never both.

**`shared-utils` is the root.** It owns coroutines + datetime + `BuildKonfig`-generated config, plus `PlatformInfo` (the module's only `expect/actual`: OS name/version + device model) and `FeedbackEmail` (pure-Kotlin `mailto:` draft builder). `AppResult<D, E : AppError>` (sealed `Success`/`Failure`, with `CommonError` + `fold(...)`) lives here too — it is the toolkit-wide result envelope, so any `*-api` (backend, database, monetization) returns it without a sibling `*-api`→`*-api` dependency. Every `*-api` interface returns `AppResult` rather than throwing — preserve this when adding new interfaces, because callers rely on exhaustive `when` for error handling.

**`shared-ui-api` was split at restructure Stage 6** into **`:core-mvi`** + **`:core-nav`** + **`:haptics`**; `:shared-ui-api` is now a src-less **facade** (`frnk/core/ui-api-facade`) re-exporting all three until the Stage 9 coordinate flip. **`:core-mvi`** owns the MVI engine: `MviContract` (`UiState` / `UiIntent` / `UiEffect` markers), `MviViewModel<S, I, E>` (StateFlow + intent SharedFlow + effect Channel), and `UiText`. **`:core-nav`** owns the **type-safe Navigation3 contract** (`ui/nav/`): `ToolkitRoute` (a `@Serializable sealed interface ToolkitRoute : NavKey` catalogue of default routes), the back-stack helpers (`NavBackStack<NavKey>.navigateTo`/`back`/`clearAndNavigateTo`), the `FrnkPendingRouteRequest` deep-link signal, the `FrnkPrimaryActionRegistry`, and the `frnkNavConfiguration(hostRoutes)` `SavedStateConfiguration` builder. **No Compose deps in either** — the nav3 *runtime* is pure Kotlin/MP, so feature ViewModels (and MVI nav-effect handlers) compile without dragging in `compose.runtime`. Routes are `@Serializable` (`:core-nav` applies `kotlin-serialization` + depends on `kotlinx-serialization-core` — **core, not json**; nav3 encodes routes via savedstate's `SavedStateEncoder`) and depend on `androidx-navigation3-runtime` (`NavKey`/`NavBackStack`). New screens subclass `MviViewModel`, write a pure reducer in `setState { copy(...) }`, and override `onIntent` for side-effectful work (using `emit(effect)` for one-shots). The **Compose bindings** for both engine and navigation — `FrnkMviScreen` + `EffectCollector` (`ui/mvi/`) and `FrnkNavDisplay` + `rememberFrnkNavBackStack` + `rememberFrnkTabbedBackStacks` + the slide animations (`ui/nav/`) — live up in **`:ui-scaffolds`** (since restructure Stage 7; they were in `:shared-ui-atoms`), since binding needs `compose.runtime`.

**`shared-ui-atoms` was split at restructure Stage 7** into **`:ui-theme`** (`frnk/ui/theme` — tokens `ui/tokens/*` + theme engine `ui/theme/*`: `FrnkTheme`/`FrnkThemeConfig`/`FrnkStrings`/`FrnkIcons`/`FrnkRipple`), **`:ui-components`** (`frnk/ui/components` — the dir `shared-ui-atoms` used to occupy; `ui/atoms/*` + `ui/molecules/*` + `ui/organisms/*` + `ui/placeholder/*`), and **`:ui-scaffolds`** (`frnk/ui/scaffolds` — `ui/scaffolds/*` + the Compose MVI bindings `ui/mvi/*` + the Compose nav bindings `ui/nav/*`). The multihaptic **engine** moved down into `:haptics` (Stage 7a). `:shared-ui-atoms` is now a src-less **facade** (`frnk/ui/atoms-facade`) `api()`-re-exporting `:ui-theme` + `:ui-components` + `:ui-scaffolds` (+ `:haptics`) until the Stage 9 coordinate flip; `:shared-ui-nav` stays on it as the still-invisibility proof. Dependency floor-to-ceiling: `haptics ← ui-theme ← ui-components ← ui-scaffolds ← ui-bottom-nav ← ui-app`. The design system (described below as one unit for orientation) now lives across those three modules:
- Headless Compose atoms built on `compose-unstyled` 2.x (the granular `com.composables:composeunstyled-{primitives,theming,platformtheme,button,icon,separators}` + `icons-lucide-cmp` artifacts; **not** `com.composables:core` and **not** Material3). The **only** sanctioned Material3 dependency in the whole toolkit lives in `:shared-ui-nav` (see below) — it stays out of `:shared-ui-atoms` and every other module.
- Design tokens (`ui/tokens/`): `FrnkColors` (Light/Dark), `FrnkTypography`, `FrnkSpacing`, `FrnkShapes`, `FrnkIconSize`.
- Theme engine (`ui/theme/`): `FrnkTheme(config, content)` over `buildPlatformTheme`, with `ThemeProperty<T>`/`ThemeToken<T>` axes (colors, textStyles, shapes, strings, icons), animated light/dark palette via `LocalAppearanceController`, and `FrnkThemeConfig` as the single host-override entry point. `FrnkStrings`/`FrnkIcons` ship default registries that hosts override per-token. `FrnkTheme` also installs `LocalFrnkHaptics` (a `multihaptic`-backed `HapticFeedback`) so atoms vibrate on interaction with zero host wiring — same precedent as the ambient ripple.
- Haptics: the `top.ltfan.multihaptic` binding behind the Compose-free `HapticFeedback`/`HapticType` contract — **both contract and engine now live in `:haptics`** (the engine binding moved down from `:shared-ui-atoms` at restructure Stage 7a; `:ui-theme`'s `FrnkTheme` installs `LocalFrnkHaptics`). `LocalFrnkHaptics.current.perform(HapticType.Success)` is the host-facing one-liner; `rememberFrnkHaptics()` resolves the platform `Vibrator` (no Context plumbing); interactive atoms call `perform(...)` on press, gated by the enabled flag the Settings "Haptic feedback" toggle drives. Treated as a UI-feedback concern (like the ripple), **not** an api/impl backend split. No native cinterop, so the XCFrameworks stay clean.
- Atoms (`ui/atoms/`): `FrnkText`, `FrnkButton`, `FrnkIcon`, `FrnkIconButton`, `FrnkDivider`, `FrnkSwitch`, `FrnkSegmentedControl`, `FrnkBottomNavBar` (floating pill), `FrnkTopAppBar` (status-bar-safe, with a search mode). Each takes an `@Immutable *State` class and separate callback lambdas; styling resolves from `Theme[colors][...]` / `Theme[textStyles][...]`.
- Molecules (`ui/molecules/`, P4-1 — small compositions of atoms + tokens, above atoms / below scaffolds): `FrnkListRow` (title/subtitle/leading-icon/trailing-slot row, optional whole-row `onClick`, optional swipe via `FrnkSwipeable`), `FrnkLabeledValue` (label + value, inline/stacked), `FrnkEmptyState` (icon/title/subtitle + optional CTA), and `FrnkSwipeable` (+ `FrnkSwipeAction`/`FrnkSwipeController`) — a generic swipe-to-action primitive (Dismiss/Reveal behaviors) usable around any content, a **headless, Material3-free** reimplementation. Same rules as atoms (`@Immutable *State`, callbacks before `modifier`, tokens-only, recorded skeleton decision, automatic ripple/haptics).
- Organisms (`ui/organisms/`, P4-2 — self-contained UI *sections* composed from molecules + atoms, above molecules / below scaffolds): `FrnkListSection` (titled card of `FrnkListRow`s, per-row click + trailing slot), `FrnkProfileHeader` (avatar + name/subtitle + stat tiles). Both lean on the internal `FrnkSectionCard` chrome primitive (shared with the Settings scaffold). Same conventions as molecules; pure view code, previews only — no unit tests (P4-4 added Compose UI tests for the highest-value **atoms** only; molecules/organisms stay previews-only).
- Scaffolds (`ui/scaffolds/`, above atoms / below features): `OnboardingScreen`, `SettingsScreen`, `BottomNavScaffold`, `HomeScreen` (each VM-backed + a stateless `*Content`), plus `FrnkScreenScaffold` — the standard top-bar-over-edge-to-edge-scrollable-content template, with the top bar and the host's floating bottom bar pinned (always visible) while content scrolls underneath them. `HomeScreen` is the home-tab template: a pinned `FrnkTopAppBar` over a **scaffold-owned** scrolling `Column` the host fills through a `ColumnScope` `content` slot (merged padding applied for it; hosts needing `LazyColumn` drop to `FrnkScreenScaffold`); its pass-through `HomeViewModel` re-emits every interaction as a `HomeEffect`. `rememberDefaultSettingsState` accepts `extraSections` + `extraSectionsPlacement` (`AfterAppearance`/`BeforeSubscription`/`BeforeLegal` default/`End`) so hosts inject custom Settings sections without hand-building the state. `FeedbackEmailLauncher` opens the platform mail composer through `shared-utils`' `FeedbackEmail` + `PlatformInfo`.
- Primary-action (FAB) routing (`ui/nav/FrnkPrimaryActionHandler.kt` + `:core-nav`'s `FrnkPrimaryActionRegistry`): the **currently active screen** claims the bottom bar's Create/Add button via `FrnkPrimaryActionHandler { onIntent(...) }` (DisposableEffect-scoped, last-registered-wins, MVI-pure); `FrnkTabbedNavScaffold(primaryActionRegistry = …)` provides `LocalFrnkPrimaryActionRegistry` and prefers a screen claim over its host-level `onPrimaryAction` fallback (button hidden when neither). Don't hand-roll `currentTabKey` conditionals.
- `@Preview` composables live in a dedicated `commonDebug` source set (`src/commonDebug/kotlin/.../previews/`) attached as `dependsOn` parent of `androidMain` + both iOS source sets, so previews compile cross-platform. AGP-9-KMP single-compilation caveat: `commonDebug` also ends up in release AARs today (inert composables, R8 strips); promote to a sibling module if true exclusion becomes load-bearing.

**`shared-ui-nav` is the platform-adaptive bottom navigation — and the toolkit's SOLE Material3 dependency.** It owns `FrnkAdaptiveBottomNavBar` (a native UIKit `UITabBar` on iOS / Material3 `NavigationBar` on Android, built on [Calf](https://github.com/MohamedRejeb/Calf)'s `AdaptiveNavigationBar`, themed from `FrnkTheme` tokens not platform defaults), two scaffolds — `FrnkAdaptiveBottomNavScaffold` (+ stateless `…Content`, the **index-based** default reusing atoms' `BottomNavViewModel`/`BottomNavScaffoldState`, for single-screen tabs) and `FrnkTabbedNavScaffold` (the **nav3 multiple-back-stack** scaffold: a host hands it `rememberFrnkTabbedBackStacks(navTabs)` + an `entryProvider` and it owns the `FrnkNavDisplay` + persistent bar + tab switching + back convention + bar-inset, for tabs that need their own back stacks / pushed detail screens) — and `rememberFrnkBottomNavState(middleTabs = …)` (enforces the Home + Settings bookends). Calf hard-depends on `compose.material3`, so Material3 reaches every consumer of this module (and of `:ui-app` above it) — a deliberate, host-approved trade isolated to this one module so `:ui-components`/`:ui-theme`/`:ui-scaffolds` stay `compose-unstyled`-only. Calf is pure Kotlin/Compose (no extra native cinterop), so the XCFramework still links under the consumer's `dynamic_lookup`. For the Material-free floating pill, use `FrnkBottomNavBar` in `:ui-components` instead. **Do not add Material3 to any other module.** The module also owns **`FrnkAppShell`** (`ui/app/`) — the one-call app shell: `FrnkTheme` wrap + nav config + Home/middle/Settings tabs + `FrnkTabbedNavScaffold` + built-in Home (`HomeScreen` slot) / Settings (default catalogue + `extraSections`) / optional Onboarding destinations + deep-links + the primary-action registry, with every extension point handed a `FrnkAppScope` (`navigateTo`/`back` + registry). Assumes Koin is started; `:ui-app`'s `FrnkAppScaffold` is the batteries-included layer over it.

**`shared-monetization-ui` is the frnk-owned paywall + subscription-management UI** (above `shared-monetization-api`, no RevenueCat dependency itself): the `PaywallScreen`/`PaywallViewModel` MVI screen wired through `frnkPaywallDestination(...)` (a `NavGraphBuilder` extension) + `paywallScaffoldModule` (Koin), and the host-facing `rememberFrnkSettingsHandler()` (backed by an internal `platformManageSubscriptionsUrl()` `expect/actual` that supplies the platform's native subscription-management URL to open). The demo and `:ui-app` both consume it; it's the toolkit's monetization *view* layer, distinct from the api/impl backend split.

**Public entry points are the individual modules.** Android hosts depend on the `dev.jdgarita.frnk:<module>` coordinates they use (composite-build substitution matches by name); iOS hosts build their own umbrella XCFramework exporting those modules (see `docs/HOST_INTEGRATION.md` §6). There is no prebuilt toolkit framework.

**`:shared-demo` is demo-only.** A KMP module that owns the cross-platform `DemoScreen` composable, `DemoViewModel` (MVI), `demoModule` (Koin bindings with `FakeEntitlementProvider` + the frnk `monetizationModule`/`paywallScaffoldModule` + `FakeKeyValueStore` + logging fakes), and an iOS `MainViewController()` factory that Swift mounts via `UIViewControllerRepresentable`. It produces its own `DemoKit.xcframework`. Critically, `:shared-demo` depends only on the `*-api` modules + `:ui-theme`/`:ui-components`/`:ui-scaffolds` (re-pointed from the `:shared-ui-atoms` facade at Stage 7, since Kotlin/Native `export` is non-transitive) + `shared-ui-nav` + `shared-monetization-ui` (no `*-impl` in common) — so `DemoKit`'s **common** surface stays free of RevenueCat / SQLite native cinterops. **`iosMain` exceptions** add two native cinterops so the iOS demo exercises real paths (each supplied by `iosDemoApp` via SPM under `dynamic_lookup`): **CrashKiOS** (`co.touchlab.crashkios:crashlytics`, BACKLOG P1-5b) for the "Force crash" → Crashlytics test, and **RevenueCat** (`purchases-kmp`, BACKLOG P3-3) so `bootstrapDemoKoinWithRevenueCat(apiKey)` installs the real `revenueCatModule` over the fake provider against the RevenueCat **Test Store**. So `iosDemoApp` links the native **Firebase + RevenueCat** SDKs (via SPM) + ships `GoogleService-Info.plist` and no longer boots on a bare simulator. Both demos share `bootstrapDemoKoin()`; `androidDemoApp` overrides with `firebaseObservabilityModule` + (when a key is set) `revenueCatModule`, and `iosDemoApp` uses `bootstrapDemoKoinWithRevenueCat(...)` (the iOS crash hook + `FirebaseApp.configure()` are wired separately in Swift). Production consumers never touch `:shared-demo`; they depend on the individual toolkit modules (own umbrella framework on iOS).

**iOS linker quirk.** Umbrella frameworks that bundle `shared-monetization-revenuecat` (DemoKit; host frameworks) set `linkerOpts("-undefined", "dynamic_lookup")` because that module cinterops the native purchases-ios SDK — expected to be supplied by the consumer Xcode project via CocoaPods or SPM. Deferring symbol resolution lets the XCFramework link locally; the consumer app's own link step resolves the native RevenueCat/Firebase symbols at integration time.

## Ktlint runs locally, not in CI

`./build.gradle.kts` applies the ktlint plugin to **all** projects with `ignoreFailures.set(false)`. Style is enforced via a **git pre-commit hook** (`.githooks/pre-commit`) that runs `./gradlew ktlintFormat` and re-stages the fixed files — so commits land already-formatted and CI no longer needs a separate ktlint job.

The hook activates automatically: the root build registers an `installGitHooks` task that points `core.hooksPath` at `.githooks/`, and it's wired to `prepareKotlinBuildScriptModel` so IDE sync (or any `./gradlew` invocation that triggers it) installs the hook. To install manually: `./gradlew installGitHooks`. To bypass for one commit: `SKIP_KTLINT=1 git commit ...` or `git commit --no-verify`.

## CI

`.github/workflows/main.yml` is a single job that runs `compileAndroidMain :androidDemoApp:compileDebugKotlin` followed by `testAndroidHostTest :androidDemoApp:testDebugUnitTest`, both with `--parallel --build-cache`. Compile covers `commonMain`+`androidMain` for every shared module (iOS targets are skipped on Linux runners) plus the demo app's Kotlin. The `compileAndroidMain` task name comes from the AGP 9 KMP-Android plugin — `compileDebugKotlinAndroid` no longer exists for KMP modules. Tests cover `commonTest`+`androidHostTest`: the AGP 9 KMP-Android plugin names the host unit-test task **`testAndroidHostTest`** (there is no `testDebugUnitTest` for KMP modules), and each tested module must opt in with `kotlin { android { withHostTest {} } }`. `:androidDemoApp` is a `com.android.application`, so its unit tests stay on `testDebugUnitTest`. No `assemble`, no `allTests`, no `ktlintCheck` — those are heavier than what CI needs to gate merges.

## Conventions to follow when adding code

- New backend call: define the interface + DTOs in `:analytics-api`, add the concrete impl in `:analytics-impl`, register the binding in `FirebaseBackendModule.kt`. Return `AppResult`, never throw.
- New persisted entity: **the toolkit owns no schema** (restructure Stage 4 / OQ-2) — relational entities belong to the consuming app. The host (or `demo/shared` for demo scaffolding) applies the SQLDelight plugin, owns the `.sq` files + database class, and builds it through `:data-db-api`'s `SqlDriverFactory` (bound by `databaseModule` in `:data-db-impl`); see `docs/HOST_INTEGRATION.md` §1 and the demo's `DemoDB`/`demoNotesModule` as the worked example.
- New key-value preference: don't reach for raw `KeyValueStore` keys — use the typed `Preference<T>` layer in `:data-prefs-api` (`Preference.kt`, P4-3). `KeyValueStore.stringPreference/booleanPreference/intPreference/enumPreference(key, default)` return a `ReadWriteProperty`, so hosts write `var fooEnabled by store.booleanPreference("foo", false)`. Int/Enum encode losslessly over the String primitive (unknown/corrupt values fall back to the default; enum decode never throws). `Long`/`Double`/nullable-string are deliberately deferred.
- New screen: state/intent/effect types + a `MviViewModel` subclass in the feature module (depend on `:core-mvi`/`:core-nav` if no Compose is needed, or `:ui-scaffolds` for the composable bindings / `:ui-components` for atoms). Compose the UI with `Frnk*` atoms under a `FrnkTheme { ... }`. Prefer the toolkit's binding primitive **`FrnkMviScreen(viewModel, topBar, onEffect) { state, onIntent, padding -> … }`** (in `:ui-scaffolds`, `ui/mvi/`) — it collects state lifecycle-aware, renders the standard `FrnkScreenScaffold`, and handles effects. For a screen that isn't the standard top-bar template, collect state with `collectAsStateWithLifecycle()` and consume effects with **`EffectCollector(vm.effects) { … }`** rather than a hand-rolled `LaunchedEffect(vm) { vm.effects.collect(...) }`. The effect channel is single-consumer — collect it in exactly one place (pass `onEffect = null` to `FrnkMviScreen` when a shared VM's effects are handled elsewhere, as the demo's Home tab does).
- New navigation flow: the toolkit uses **AndroidX Navigation3**. Define `@Serializable` route types implementing `NavKey` (extend `ToolkitRoute` or declare your own; the route-owning module needs the `kotlin-serialization` plugin). Build the saved-state config with **`frnkNavConfiguration(hostRoutes = SerializersModule { polymorphic(NavKey::class) { subclass(…) } })`** (registers your routes alongside the toolkit's), create the host-owned back stack with **`rememberFrnkNavBackStack(config, startRoute)`**, and render **`FrnkNavDisplay(backStack)`** (`:ui-scaffolds`, `ui/nav/`) — it bakes in the saveable-state + ViewModel-store entry decorators and the slide transitions. Register destinations either via Koin's `navigation<Route> { … }` DSL (the default `koinEntryProvider()`) or a local `entryProvider { entry<Route> { … } }`. Drive navigation as a **`UiEffect`**: a ViewModel emits it, a single `EffectCollector` above the host mutates the back stack via `backStack.navigateTo(route)` / `back()` / `clearAndNavigateTo(route)` — collect in exactly one place (single-consumer channel). For a bottom-nav with **multiple back stacks**, the one-call path is **`FrnkTabbedNavScaffold(tabbed, tabs = navTabs, hideBarFor, entryProvider)`** (`:shared-ui-nav`): build `navTabs: List<FrnkNavTab>` (key + root + icon + label, declared once), create the host-owned `tabbed` with **`rememberFrnkTabbedBackStacks(config, navTabs = navTabs)`**, and the scaffold owns the `FrnkNavDisplay` + persistent adaptive bar + `switchTo`/`resetCurrentToRoot` + `FrnkTabbedBackHandler` (back from a non-home tab root → home) + full-screen bar hiding (`hideBarFor` **defaults to `{ it is FrnkFullScreenRoute }`** — mark a route with the `FrnkFullScreenRoute` marker interface to hide the bar on it, rather than maintaining a separate predicate) + the bottom-inset (via `LocalFrnkBottomBarInset`, so screens on `FrnkScreenScaffold`/`FrnkMviScreen` reserve the bar automatically). Pass a **remembered** `navTabs` list (a plain `List` is an unstable Compose param). The host keeps owning `tabbed` so its single `EffectCollector` can drive `tabbed.current.navigateTo(route)`. `FrnkTabbedNavScaffold` is the Material3 adaptive-bar scaffold; for multiple-back-stack nav3 **without** Material3, hand-wire the lower-level primitives — `rememberFrnkTabbedBackStacks` + `FrnkNavDisplay(backStack = tabbed.current)` + `FrnkTabbedBackHandler` + your own bar (e.g. the Material-free `FrnkBottomNavBar` pill). For a finished flow use `clearAndNavigateTo(route)`. On Android `NavDisplay` auto-pops system/predictive back *within* a tab (host activity sets `android:enableOnBackInvokedCallback="true"`); on iOS also give pushed screens an on-screen back affordance. `:shared-demo`'s `DemoScreen` is the reference integration; deep-link in via `FrnkPendingRouteRequest`.
- New host app spin-up: the highest-level path is **`FrnkAppScaffold(appName, appVersion, …) { homeContent }`** (`:ui-app`) after `initializeFrnk(context = this, modules = frnkUiModules() + …)` (Android) / `initializeFrnk(modules = …)` (iOS, both in `:core-di`) — it wraps **`FrnkAppShell`** (`:shared-ui-nav`, `ui/app/`), which owns the theme + nav config + Home/middle/Settings tabs + built-in Home (`HomeScreen` content slot) / Settings (default catalogue + `settingsExtraSections`) / optional Onboarding (`onboardingPages`) destinations + deep-links + the primary-action registry. Host extension points (`entries`, `effects`, effect handlers) receive a **`FrnkAppScope`** (`navigateTo`/`back` + registry); never re-register the built-in routes in `entries` (nav3 throws on duplicates). Modules that can't see `:ui-app` (like `:shared-demo`) compose `FrnkAppShell` directly. See `HOST_ALIGNMENT.md` §3b.
- **State hoisting over local state.** Screen / navigation / business state lives in the feature's `MviViewModel` (`*State` + `*Intent`), never as `var … by remember { mutableStateOf(…) }` inside a composable. Composables stay stateless: read from the collected `state`, emit `onIntent(...)`. Reserve `remember` / `rememberSaveable` for genuinely-local UI holders (scroll / pager / focus / animation state, and `remember`-derived builders like `rememberFrnkNavController`). The atoms and scaffolds already follow this — match them.
- New atom: live under `frnk/ui/components/src/commonMain/.../ui/atoms/`. Model its `*State` as a **`sealed interface` with a `Content` data class + a `data object Skeleton`** (add an `Error` data class where there's a real error visual) — this is the toolkit's mandated state shape (see `HOST_ALIGNMENT.md` → "Component style guide"). The composable takes `state` + callbacks + `modifier` and `when`-switches on the sealed state. Read styling from `Theme[colors][...]` / `Theme[textStyles][...]` and spacing/sizes from `Theme[spacing][...]` / `Theme[iconSizes][...]`, never hardcoded `Color(0xFF...)` or raw `.dp`. Add a `@Preview` to `src/commonDebug/.../previews/` using `PreviewSurface(appearance = ...)`. **Always ask whether the atom needs a loading skeleton.** If yes (most content-bearing atoms do), the `Skeleton` branch renders a **non-interactive** placeholder via `Modifier.frnkSkeleton(FrnkSkeleton(enabled = true), shape = <the atom's natural shape token>)` (no clickable/toggleable node) while `Content` renders the real UI; if the atom paints a brand color, the `Skeleton` branch simply doesn't paint it (no fill to peek through). Showcase the `Skeleton` state in the demo + a `@Preview`. If a skeleton genuinely doesn't apply (e.g. a pure divider, a terminal empty state), keep the state non-sealed / skip the object and say why. (`FrnkText` is the documented exception that also keeps a per-subtype `skeleton` field for content-sized text skeletons.) **Press feedback is automatic**: `FrnkTheme` installs a ripple as `LocalIndication`, so any atom built on `UnstyledButton` / `Modifier.clickable` / `selectable` / `toggleable` ripples with no extra wiring — don't pass an `indication` unless you deliberately want a different one. Host apps apply the same ripple to their own components via `rememberFrnkRipple()`. **Haptics are automatic too**: interactive atoms call `LocalFrnkHaptics.current.perform(HapticType.Click)` (buttons) or `.perform(HapticType.Selection)` (toggles/selectors) on interaction, gated by the global enabled flag — wire new interactive atoms the same way rather than hand-rolling vibration.
- New molecule / organism (compositions between atoms and scaffolds): molecules live under `frnk/ui/components/src/commonMain/.../ui/molecules/`, organisms under `.../ui/organisms/`. Same rules as atoms — `@Immutable *State`, callbacks before `modifier`, tokens-only styling, automatic ripple/haptics (don't re-wire), a `@Preview` in the matching `commonDebug/.../previews/` package, and a recorded skeleton decision. They're pure view code, previews only — no unit tests (P4-4 added Compose UI tests for the highest-value **atoms** only; molecules/organisms stay previews-only). Reuse the **public** `FrnkSectionCard` (in `:ui-components` `ui/organisms/`; promoted from `internal` at Stage 7b since the Settings scaffold now consumes it cross-module from `:ui-scaffolds`) for titled-card chrome rather than re-rolling it.
- New adaptive-nav surface: goes in `:shared-ui-nav` (`ui/bottomnav/`) — the **only** module allowed a Material3 dependency. Don't add Material3 anywhere else; for a Material-free bar use atoms' `FrnkBottomNavBar` pill.
- New scaffold (fixed-shape page template above atoms, below features): live in `:ui-scaffolds` under `frnk/ui/scaffolds/src/commonMain/.../ui/scaffolds/`. Expose **both** a stateless `*Content(state, onIntent, modifier)` primitive (used by previews + advanced hosts) and a VM-backed convenience composable that resolves an `MviViewModel` via `koinViewModel { parametersOf(initialState) }`. Register the VM in a per-scaffold Koin module (`xxxScaffoldModule`) that downstream Koin modules `includes(...)`. Default copy goes through `FrnkStrings` so hosts can override per-token.
- New tests: write **platform-agnostic** ones (reducers, `*-api` logic) in the module's `commonMain`-sibling `commonTest` source set; tests that need a platform-only runtime go in `androidHostTest` instead (Compose UI + Robolectric in `:ui-components`/`:ui-scaffolds`, the JDBC driver in `demo/shared`'s NoteStore round-trip). Note `:ui-components`/`:ui-scaffolds` have **no** `commonTest` source set — their tests are all `androidHostTest` (both apply the `frnk.kmp.library.composehosttest` convention plugin, which supplies the `withHostTest{isIncludeAndroidResources}` + Robolectric bundle + the `commonDebug` preview wiring). A KMP module only gets a host unit-test compilation after opting in with `kotlin { android { withHostTest {} } }` and adding `commonTest.dependencies { implementation(libs.kotlin.test); implementation(libs.kotlinx.coroutines.test) }`; the task is **`testAndroidHostTest`** (not `testDebugUnitTest`). Reducer tests follow `MviViewModelTest` in `:core-mvi` (set `Dispatchers.setMain` since `viewModelScope` drives the intent collector); fakes for `*-api` interfaces follow `FakeAnalyticsTracker` in `:analytics-api` `commonTest`. Reducers and `*-api` logic should land with tests. **Compose UI tests for the design system are the exception** (P4-4): they need a real composition + Robolectric, which have no common/iOS variant, so they live in `:ui-components`'s (atoms) / `:ui-scaffolds`'s (scaffolds) **`androidHostTest`** source set (not `commonTest`) and extend `RobolectricComposeTest` — they still run on `testAndroidHostTest`. See `frnk/ui/components/CLAUDE.md` + `frnk/ui/scaffolds/CLAUDE.md`.
- iOS-visible API surface: anything Swift needs to call must be in a module the consumer's umbrella framework `export(...)`s (for the demo: `:shared-demo`'s `DemoKit` export list).
- **Every new feature is demoed in all three demo layers.** A feature isn't done until it's exercised in `:shared-demo` (cross-platform), `androidDemoApp` (installs and runs on a device/emulator), and `iosDemoApp` (builds the `DemoKit.xcframework` and runs in a simulator). If a feature genuinely can't be demoed (e.g., a build-time-only refactor), say so explicitly and explain why.

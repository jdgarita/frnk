# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`frnk` is a Kotlin Multiplatform + Compose Multiplatform **toolkit** (not a standalone app) intended to be consumed by downstream apps as a Git submodule via a Gradle composite build (`includeBuild("../frnk")`). The `androidDemoApp` / `iosDemoApp` directories exist only as internal smoke harnesses — they are not the shipping product.

Read `docs/ARCHITECTURE.md` first when reasoning about cross-module changes; it is the canonical description of the module graph and the api/impl split.

## Common commands

Bootstrap (one-time per checkout):
```bash
cp local.properties.template local.properties   # then fill in Supabase/Firebase keys; BuildKonfig reads from this
```

Day-to-day:
```bash
./gradlew compileAndroidMain                # fast compile-only check (what CI runs — covers commonMain+androidMain for every KMP module); Gradle parallelises across modules
./gradlew testAndroidHostTest               # commonTest + androidHostTest across all KMP modules (what CI runs); :androidDemoApp uses testDebugUnitTest
./gradlew :shared-database-impl:testAndroidHostTest   # run a single module's tests
./gradlew ktlintFormat                      # auto-fix style (also runs from the pre-commit hook)
./gradlew assemble                          # full build of every target — only when producing release artifacts
./gradlew :iosApp:assembleFrnkKitReleaseXCFramework  # produce iosApp/build/XCFrameworks/release/FrnkKit.xcframework
./gradlew :shared-demo:assembleDemoKitDebugXCFramework  # produce shared/shared-demo/build/XCFrameworks/debug/DemoKit.xcframework (iosDemoApp consumes this)
./gradlew clean
```

`local.properties` is gitignored and required — `BuildKonfig` will fail at configuration time without `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `FIREBASE_*`, and `BUILD_VARIANT`.

`iosDemoApp` needs local setup beyond `local.properties`: drop in its own `GoogleService-Info.plist` and let Xcode resolve Swift packages on first open (Firebase SDK). Both are gitignored — `GoogleService-Info.plist` and the Xcode-managed `**/xcshareddata/swiftpm/Package.resolved` — so a fresh checkout of the demo isn't buildable from CI (which never builds iOS anyway); it's a local-only harness.

## Toolchain pinning (don't fight it)

- **JDK 17** everywhere. Android Studio bundles JDK 21; the Foojay resolver in `settings.gradle.kts` auto-provisions 17, and every KMP module explicitly calls `kotlin { jvmToolchain(17) }` because AGP's javac and the Kotlin task would otherwise disagree about target. Don't change this without changing both sides.
- **Kotlin 2.3.21 + AGP 9.2.1 + Gradle 9.5.1.** AGP 9 forbids combining `org.jetbrains.kotlin.multiplatform` with `com.android.library` in the same subproject — every KMP-Android module here applies `com.android.kotlin.multiplatform.library` (alias `libs.plugins.android.kotlin.multiplatform.library`) and configures the Android side via `kotlin { android { … } }`, not a top-level `android {}` block. Compile/min SDK live inside that nested block.
- `:androidDemoApp` (the only `com.android.application`) uses AGP 9's **built-in Kotlin** — it does **not** apply `kotlin.android`. Don't re-add that plugin.
- Shared constants (package name, min/compile/target SDK, iOS framework name `FrnkKit`, database class name `FrnkDB`) live in `buildSrc/src/main/kotlin/ProjectConfiguration.kt`. Read from there rather than hardcoding. AGP 9 caps compileSdk at 36.

## Architecture you need to respect

**Directory layout vs Gradle paths.** All `shared-*` modules (plus `shared-utils` and `shared-demo`) physically live under the `shared/` directory — alongside the `:shared` aggregator's own `build.gradle.kts` + `src/`. Their Gradle paths stay **flat** (`:shared-utils`, `:shared-ui-atoms`, …), so type-safe project accessors (`projects.sharedUtils`, …) and `:module` task paths are unchanged. `settings.gradle.kts` reconciles the two by remapping each module's `projectDir` to `shared/<name>` after `include(...)`. When referencing a module's files on disk, prefix with `shared/` (e.g. `shared/shared-ui-atoms/src/...`); when referencing it as a Gradle project, don't (e.g. `:shared-ui-atoms`, `projects.sharedUiAtoms`).

**`:shared` is the only consumer-facing module.** It aggregates every `shared-*` module via `api(...)` — both interfaces and implementations — and exposes `frnkModules(BackendChoice, ObservabilityChoice)` + `initializeFrnk()` for one-shot Koin bootstrap. `androidApp` and `iosApp` each depend on `:shared` only, and re-export it.

**api/impl module split.** Each domain that pulls in a third-party SDK has two modules:

- `shared-backend-api`, `shared-database-api`, `shared-monetization-api` — pure-interface, no Ktor / no SQLDelight / no RevenueCat. Domain code depends on these.
- `shared-backend-firebase`, `shared-backend-supabase`, `shared-database-impl`, `shared-monetization-revenuecat` — concrete bindings exposed as Koin modules (`firebaseBackendModule`, `supabaseBackendModule`, `databaseModule`, `revenueCatModule`).

The point is swap-ability and parallel compilation. **Do not** add a third-party SDK dependency to an `*-api` module, and do not call into an `*-impl` package from anywhere except `:shared`'s Koin wiring.

**Backend choice is runtime, not compile-time.** `:shared` bundles both `shared-backend-firebase` and `shared-backend-supabase`. `frnkModules(BackendChoice.Supabase)` registers `supabaseBackendModule`; `BackendChoice.Firebase` registers `firebaseBackendModule`. The unchosen backend's Koin module is simply never installed, so its bindings never appear in the graph.

**Observability is a separate axis from the backend.** `ObservabilityChoice` (`None` default / `Firebase`) selects analytics + crash reporting **independently of `BackendChoice`** — a local-only or Supabase-backed app can still ship Firebase telemetry. `None` installs `noopObservabilityModule` (over `shared-backend-api`'s `Noop{Analytics,Crash}`); `Firebase` installs `firebaseObservabilityModule` (in `shared-backend-firebase`). Same never-installed-when-unchosen rule as the backend axis.

**`shared-utils` is the root.** It owns coroutines + datetime + `BuildKonfig`-generated config, plus `PlatformInfo` (the module's only `expect/actual`: OS name/version + device model) and `FeedbackEmail` (pure-Kotlin `mailto:` draft builder). `AppResult<D, E : AppError>` (sealed `Success`/`Failure`, with `CommonError` + `fold(...)`) lives here too — it is the toolkit-wide result envelope, so any `*-api` (backend, database, monetization) returns it without a sibling `*-api`→`*-api` dependency. Every `*-api` interface returns `AppResult` rather than throwing — preserve this when adding new interfaces, because callers rely on exhaustive `when` for error handling.

**`shared-ui-api`** owns the MVI engine: `MviContract` (`UiState` / `UiIntent` / `UiEffect` markers), `MviViewModel<S, I, E>` (StateFlow + intent SharedFlow + effect Channel), and `UiText`. It also owns the **type-safe navigation contract** (`ui/nav/`): `ToolkitRoute` (a `@Serializable` sealed catalogue of default routes) and the Compose-free `FrnkNavigator` / `FrnkNavOptions` abstraction. **No Compose deps here** — feature ViewModels (and MVI nav-effect handlers) compile without dragging in `compose.runtime`. Routes are `@Serializable` (the module applies `kotlin-serialization` + depends on `kotlinx-serialization-core` — **core, not json**; navigation-compose encodes routes via its own `SavedStateEncoder`). New screens subclass `MviViewModel`, write a pure reducer in `setState { copy(...) }`, and override `onIntent` for side-effectful work (using `emit(effect)` for one-shots). The **Compose bindings** for both engine and navigation — `FrnkMviScreen` + `EffectCollector` (`ui/mvi/`) and `FrnkNavHost` + `frnkComposable` + `rememberFrnkNavigator` (`ui/nav/`) — live one layer up in `:shared-ui-atoms`, since binding needs `compose.runtime`.

**`shared-ui-atoms`** owns the design system:
- Headless Compose atoms built on `compose-unstyled` 2.x (the granular `com.composables:composeunstyled-{primitives,theming,platformtheme,button,icon,separators}` + `icons-lucide-cmp` artifacts; **not** `com.composables:core` and **not** Material3). The **only** sanctioned Material3 dependency in the whole toolkit lives in `:shared-ui-nav` (see below) — it stays out of `:shared-ui-atoms` and every other module.
- Design tokens (`ui/tokens/`): `FrnkColors` (Light/Dark), `FrnkTypography`, `FrnkSpacing`, `FrnkShapes`, `FrnkIconSize`.
- Theme engine (`ui/theme/`): `FrnkTheme(config, content)` over `buildPlatformTheme`, with `ThemeProperty<T>`/`ThemeToken<T>` axes (colors, textStyles, shapes, strings, icons), animated light/dark palette via `LocalAppearanceController`, and `FrnkThemeConfig` as the single host-override entry point. `FrnkStrings`/`FrnkIcons` ship default registries that hosts override per-token. `FrnkTheme` also installs `LocalFrnkHaptics` (a `multihaptic`-backed `HapticFeedback`) so atoms vibrate on interaction with zero host wiring — same precedent as the ambient ripple.
- Haptics (`ui/haptics/`): the `top.ltfan.multihaptic` binding behind the Compose-free `HapticFeedback`/`HapticType` contract (in `:shared-ui-api`). `LocalFrnkHaptics.current.perform(HapticType.Success)` is the host-facing one-liner; `rememberFrnkHaptics()` resolves the platform `Vibrator` (no Context plumbing); interactive atoms call `perform(...)` on press, gated by the enabled flag the Settings "Haptic feedback" toggle drives. Treated as a UI-feedback concern (like the ripple), **not** an api/impl backend split. No native cinterop, so the XCFrameworks stay clean.
- Atoms (`ui/atoms/`): `FrnkText`, `FrnkButton`, `FrnkIcon`, `FrnkIconButton`, `FrnkDivider`, `FrnkSwitch`, `FrnkSegmentedControl`, `FrnkBottomNavBar` (floating pill), `FrnkTopAppBar` (status-bar-safe, with a search mode). Each takes an `@Immutable *State` class and separate callback lambdas; styling resolves from `Theme[colors][...]` / `Theme[textStyles][...]`.
- Molecules (`ui/molecules/`, P4-1 — small compositions of atoms + tokens, above atoms / below scaffolds): `FrnkListRow` (title/subtitle/leading-icon/trailing-slot row, optional whole-row `onClick`, optional swipe via `FrnkSwipeable`), `FrnkLabeledValue` (label + value, inline/stacked), `FrnkEmptyState` (icon/title/subtitle + optional CTA), and `FrnkSwipeable` (+ `FrnkSwipeAction`/`FrnkSwipeController`) — a generic swipe-to-action primitive (Dismiss/Reveal behaviors) usable around any content, a **headless, Material3-free** reimplementation. Same rules as atoms (`@Immutable *State`, callbacks before `modifier`, tokens-only, recorded skeleton decision, automatic ripple/haptics).
- Organisms (`ui/organisms/`, P4-2 — self-contained UI *sections* composed from molecules + atoms, above molecules / below scaffolds): `FrnkListSection` (titled card of `FrnkListRow`s, per-row click + trailing slot), `FrnkProfileHeader` (avatar + name/subtitle + stat tiles). Both lean on the internal `FrnkSectionCard` chrome primitive (shared with the Settings scaffold). Same conventions as molecules; pure view code (no unit tests, like atoms/molecules).
- Scaffolds (`ui/scaffolds/`, above atoms / below features): `OnboardingScreen`, `SettingsScreen`, `BottomNavScaffold` (each VM-backed + a stateless `*Content`), plus `FrnkScreenScaffold` — the standard top-bar-over-edge-to-edge-scrollable-content template — and `CollapsibleBarsState` / `rememberCollapsibleBarsState()`, the shared scroll coordinator that hides the top bar + floating bottom bar on scroll-down and reveals them on scroll-up, **only when the content overflows the viewport** (driven by what the content actually scrolled, via `onPostScroll`). `FeedbackEmailLauncher` opens the platform mail composer through `shared-utils`' `FeedbackEmail` + `PlatformInfo`.
- `@Preview` composables live in a dedicated `commonDebug` source set (`src/commonDebug/kotlin/.../previews/`) attached as `dependsOn` parent of `androidMain` + both iOS source sets, so previews compile cross-platform. AGP-9-KMP single-compilation caveat: `commonDebug` also ends up in release AARs today (inert composables, R8 strips); promote to a sibling module if true exclusion becomes load-bearing.

**`shared-ui-nav` is the platform-adaptive bottom navigation — and the toolkit's SOLE Material3 dependency.** It owns `FrnkAdaptiveBottomNavBar` (a native UIKit `UITabBar` on iOS / Material3 `NavigationBar` on Android, built on [Calf](https://github.com/MohamedRejeb/Calf)'s `AdaptiveNavigationBar`, themed from `FrnkTheme` tokens not platform defaults), `FrnkAdaptiveBottomNavScaffold` (+ stateless `…Content`, the default scaffold reusing atoms' `BottomNavViewModel`/`BottomNavScaffoldState`), and `rememberFrnkBottomNavState(middleTabs = …)` (enforces the Home + Settings bookends). Calf hard-depends on `compose.material3`, so Material3 ships in `FrnkKit` for **every** consumer — a deliberate, host-approved trade isolated to this one module so `:shared-ui-atoms` stays `compose-unstyled`-only. Calf is pure Kotlin/Compose (no extra native cinterop), so the XCFramework still links under the consumer's `dynamic_lookup`. For the Material-free floating pill, use `FrnkBottomNavBar` in `:shared-ui-atoms` instead. **Do not add Material3 to any other module.**

**`shared-monetization-ui` is the frnk-owned paywall + subscription-management UI** (above `shared-monetization-api`, no RevenueCat dependency itself): the `PaywallScreen`/`PaywallViewModel` MVI screen wired through `frnkPaywallDestination(...)` (a `NavGraphBuilder` extension) + `paywallScaffoldModule` (Koin), and the host-facing `rememberFrnkSettingsHandler()` (backed by an internal `platformManageSubscriptionsUrl()` `expect/actual` that supplies the platform's native subscription-management URL to open). The demo and `:shared` both consume it; it's the toolkit's monetization *view* layer, distinct from the api/impl backend split.

**Public entry points** are `androidApp` (a KMP-Android library via `com.android.kotlin.multiplatform.library`, **not** an application) and `iosApp` (a KMP target producing the fat `FrnkKit` XCFramework via `XCFramework("FrnkKit")`). Both depend on `:shared` only and re-export it. Downstream consumers depend on `dev.jdgarita.frnk:androidApp` / the XCFramework — that's it.

**`:shared-demo` is demo-only.** A KMP module that owns the cross-platform `DemoScreen` composable, `DemoViewModel` (MVI), `demoModule` (Koin bindings with `FakeEntitlementProvider` + the frnk `monetizationModule`/`paywallScaffoldModule` + `FakeKeyValueStore` + logging fakes), and an iOS `MainViewController()` factory that Swift mounts via `UIViewControllerRepresentable`. It produces its own `DemoKit.xcframework`. Critically, `:shared-demo` does **not** depend on `:shared` — only the `*-api` modules + `shared-ui-atoms` + `shared-monetization-ui` — so `DemoKit`'s **common** surface stays free of RevenueCat / SQLite native cinterops. **`iosMain` exceptions** add two native cinterops so the iOS demo exercises real paths (each supplied by `iosDemoApp` via SPM under `dynamic_lookup`): **CrashKiOS** (`co.touchlab.crashkios:crashlytics`, BACKLOG P1-5b) for the "Force crash" → Crashlytics test, and **RevenueCat** (`purchases-kmp`, BACKLOG P3-3) so `bootstrapDemoKoinWithRevenueCat(apiKey)` installs the real `revenueCatModule` over the fake provider against the RevenueCat **Test Store**. So `iosDemoApp` links the native **Firebase + RevenueCat** SDKs (via SPM) + ships `GoogleService-Info.plist` and no longer boots on a bare simulator. Both demos share `bootstrapDemoKoin()`; `androidDemoApp` overrides with `firebaseObservabilityModule` + (when a key is set) `revenueCatModule`, and `iosDemoApp` uses `bootstrapDemoKoinWithRevenueCat(...)` (the iOS crash hook + `FirebaseApp.configure()` are wired separately in Swift). Production consumers never touch `:shared-demo`; they use `FrnkKit.xcframework` from `:iosApp`.

**iOS linker quirk.** The `iosApp` framework binaries set `linkerOpts("-undefined", "dynamic_lookup")` because `:shared` bundles `shared-monetization-revenuecat`, which cinterops the native `PurchasesHybridCommon` framework — and that native framework is expected to be supplied by the consumer Xcode project via CocoaPods or SPM. Deferring symbol resolution lets the toolkit's XCFramework link locally; the consumer app's own link step resolves PurchasesHybridCommon (and any Firebase native pods) at integration time.

## Ktlint runs locally, not in CI

`./build.gradle.kts` applies the ktlint plugin to **all** projects with `ignoreFailures.set(false)`. Style is enforced via a **git pre-commit hook** (`.githooks/pre-commit`) that runs `./gradlew ktlintFormat` and re-stages the fixed files — so commits land already-formatted and CI no longer needs a separate ktlint job.

The hook activates automatically: the root build registers an `installGitHooks` task that points `core.hooksPath` at `.githooks/`, and it's wired to `prepareKotlinBuildScriptModel` so IDE sync (or any `./gradlew` invocation that triggers it) installs the hook. To install manually: `./gradlew installGitHooks`. To bypass for one commit: `SKIP_KTLINT=1 git commit ...` or `git commit --no-verify`.

## CI

`.github/workflows/main.yml` is a single job that runs `compileAndroidMain :androidDemoApp:compileDebugKotlin` followed by `testAndroidHostTest :androidDemoApp:testDebugUnitTest`, both with `--parallel --build-cache`. Compile covers `commonMain`+`androidMain` for every shared module (iOS targets are skipped on Linux runners) plus the demo app's Kotlin. The `compileAndroidMain` task name comes from the AGP 9 KMP-Android plugin — `compileDebugKotlinAndroid` no longer exists for KMP modules. Tests cover `commonTest`+`androidHostTest`: the AGP 9 KMP-Android plugin names the host unit-test task **`testAndroidHostTest`** (there is no `testDebugUnitTest` for KMP modules), and each tested module must opt in with `kotlin { android { withHostTest {} } }`. `:androidDemoApp` is a `com.android.application`, so its unit tests stay on `testDebugUnitTest`. No `assemble`, no `allTests`, no `ktlintCheck` — those are heavier than what CI needs to gate merges.

## Conventions to follow when adding code

- New backend call: define the interface + DTOs in `shared-backend-api`, add concrete impls in `shared-backend-firebase` **and** `shared-backend-supabase` (both have to satisfy the contract), register the bindings in `FirebaseBackendModule.kt` / `SupabaseBackendModule.kt`. Return `AppResult`, never throw.
- New persisted entity: add the `.sq` file under `shared-database-impl` (SQLDelight generates into `dev.jdgarita.frnk.database.sql` — set in the database module's `build.gradle.kts`); expose access through an interface in `shared-database-api`; bind in `DatabaseModule.kt`.
- New key-value preference: don't reach for raw `KeyValueStore` keys — use the typed `Preference<T>` layer in `shared-database-api` (`Preference.kt`, P4-3). `KeyValueStore.stringPreference/booleanPreference/intPreference/enumPreference(key, default)` return a `ReadWriteProperty`, so hosts write `var fooEnabled by store.booleanPreference("foo", false)`. Int/Enum encode losslessly over the String primitive (unknown/corrupt values fall back to the default; enum decode never throws). `Long`/`Double`/nullable-string are deliberately deferred.
- New screen: state/intent/effect types + a `MviViewModel` subclass in the feature module (depend on `:shared-ui-api` if no Compose is needed, or `:shared-ui-atoms` for the composable). Compose the UI with `Frnk*` atoms under a `FrnkTheme { ... }`. Prefer the toolkit's binding primitive **`FrnkMviScreen(viewModel, topBar, onEffect) { state, onIntent, padding -> … }`** (in `shared-ui-atoms`, `ui/mvi/`) — it collects state lifecycle-aware, renders the standard `FrnkScreenScaffold`, and handles effects. For a screen that isn't the standard top-bar template, collect state with `collectAsStateWithLifecycle()` and consume effects with **`EffectCollector(vm.effects) { … }`** rather than a hand-rolled `LaunchedEffect(vm) { vm.effects.collect(...) }`. The effect channel is single-consumer — collect it in exactly one place (pass `onEffect = null` to `FrnkMviScreen` when a shared VM's effects are handled elsewhere, as the demo's Home tab does).
- New navigation flow: the toolkit wraps JetBrains CMP `navigation-compose` (P2-1). Define `@Serializable` route types (extend `ToolkitRoute` or declare your own; the module needs the `kotlin-serialization` plugin). Build the graph with **`FrnkNavHost(navController, startRoute) { frnkComposable<Route> { route -> … } }`** (`shared-ui-atoms`, `ui/nav/`); `frnkComposable` decodes the typed route argument via `toRoute`. The **host owns the back stack** — create it with `rememberFrnkNavController()` and pass it in. Drive navigation as a **`UiEffect`**: a ViewModel emits it, a single `EffectCollector` above the `FrnkNavHost` routes it into a `FrnkNavigator` (`rememberFrnkNavigator(navController)`) — collect in exactly one place (single-consumer channel). Use `FrnkNavOptions(popUpTo = PopUpTo(route, inclusive, saveState), launchSingleTop, restoreState)` for tab switching (multiple back stacks) or clearing a finished flow (`inclusive = true`). On Android `NavHost` auto-pops system/predictive back (host activity sets `android:enableOnBackInvokedCallback="true"`); on iOS also give pushed screens an on-screen back affordance. `:shared-demo`'s `DemoScreen` is the reference integration.
- **State hoisting over local state.** Screen / navigation / business state lives in the feature's `MviViewModel` (`*State` + `*Intent`), never as `var … by remember { mutableStateOf(…) }` inside a composable. Composables stay stateless: read from the collected `state`, emit `onIntent(...)`. Reserve `remember` / `rememberSaveable` for genuinely-local UI holders (scroll / pager / focus / animation state, and `remember`-derived builders like `rememberCollapsibleBarsState`). The atoms and scaffolds already follow this — match them.
- New atom: live under `shared/shared-ui-atoms/src/commonMain/.../ui/atoms/`. Define an `@Immutable *State` class first; the composable takes `state` + callbacks + `modifier`. Read styling from `Theme[colors][...]` / `Theme[textStyles][...]`, never hardcoded `Color(0xFF...)` or raw `.dp`. Add a `@Preview` to `src/commonDebug/.../previews/` using `PreviewSurface(appearance = ...)`. **Always ask whether the atom needs a loading skeleton.** If yes (most content-bearing atoms do), add a `skeleton: FrnkSkeleton = FrnkSkeleton()` field to its `*State` and apply `Modifier.frnkSkeleton(state.skeleton, shape = <the atom's natural shape token>)` near the end of its visual modifier chain, gating interaction with `&& !state.skeleton.enabled`; if the atom paints a brand color under the skeleton, drop that fill while `skeleton.enabled` so its antialiased rim doesn't peek through (see `FrnkSwitch`). Showcase the skeleton in the demo + a `@Preview`. If a skeleton genuinely doesn't apply (e.g. a pure divider), say so explicitly. **Press feedback is automatic**: `FrnkTheme` installs a ripple as `LocalIndication`, so any atom built on `UnstyledButton` / `Modifier.clickable` / `selectable` / `toggleable` ripples with no extra wiring — don't pass an `indication` unless you deliberately want a different one. Host apps apply the same ripple to their own components via `rememberFrnkRipple()`. **Haptics are automatic too**: interactive atoms call `LocalFrnkHaptics.current.perform(HapticType.Click)` (buttons) or `.perform(HapticType.Selection)` (toggles/selectors) on interaction, gated by the global enabled flag — wire new interactive atoms the same way rather than hand-rolling vibration.
- New molecule / organism (compositions between atoms and scaffolds): molecules live under `shared/shared-ui-atoms/src/commonMain/.../ui/molecules/`, organisms under `.../ui/organisms/`. Same rules as atoms — `@Immutable *State`, callbacks before `modifier`, tokens-only styling, automatic ripple/haptics (don't re-wire), a `@Preview` in the matching `commonDebug/.../previews/` package, and a recorded skeleton decision. They're pure view code, so no unit tests (like atoms). Reuse the internal `FrnkSectionCard` for titled-card chrome rather than re-rolling it.
- New adaptive-nav surface: goes in `:shared-ui-nav` (`ui/bottomnav/`) — the **only** module allowed a Material3 dependency. Don't add Material3 anywhere else; for a Material-free bar use atoms' `FrnkBottomNavBar` pill.
- New scaffold (fixed-shape page template above atoms, below features): live under `shared/shared-ui-atoms/src/commonMain/.../ui/scaffolds/`. Expose **both** a stateless `*Content(state, onIntent, modifier)` primitive (used by previews + advanced hosts) and a VM-backed convenience composable that resolves an `MviViewModel` via `koinViewModel { parametersOf(initialState) }`. Register the VM in a per-scaffold Koin module (`xxxScaffoldModule`) that downstream Koin modules `includes(...)`. Default copy goes through `FrnkStrings` so hosts can override per-token.
- New tests: write them in the module's `commonMain`-sibling `commonTest` source set. A KMP module only gets a host unit-test compilation after opting in with `kotlin { android { withHostTest {} } }` and adding `commonTest.dependencies { implementation(libs.kotlin.test); implementation(libs.kotlinx.coroutines.test) }`; the task is **`testAndroidHostTest`** (not `testDebugUnitTest`). Reducer tests follow `MviViewModelTest` in `shared-ui-api` (set `Dispatchers.setMain` since `viewModelScope` drives the intent collector); fakes for `*-api` interfaces follow `FakeAuthService` in `shared-backend-api` `commonTest`. Reducers and `*-api` logic should land with tests.
- iOS-visible API surface: everything flows through `:shared`, which `iosApp` already `export`s. Anything Swift needs to call must be in a `shared-*` module that `:shared` `api()`-depends on (which is all of them). No per-module `export(...)` edits required.
- **Every new feature is demoed in all three demo layers.** A feature isn't done until it's exercised in `:shared-demo` (cross-platform), `androidDemoApp` (installs and runs on a device/emulator), and `iosDemoApp` (builds the `DemoKit.xcframework` and runs in a simulator). If a feature genuinely can't be demoed (e.g., a build-time-only refactor), say so explicitly and explain why.
